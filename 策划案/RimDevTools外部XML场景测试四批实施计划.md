## 1. 依据与交付规则

需求依据为[外部 XML 场景测试可行性与结构设计](RimDevTools外部XML场景测试可行性与结构设计.md)，包含外部回归场景、共享角色和地图定义、整套配装展示、游戏内手动测试及独立群战数值评测。四批划分以本计划为准，场景细节继续参照原设计。

最新范围明确为：既有全部非 UI 测试均须支持高度自定义的外部 XML 规则，群战另作为新增的独立数值评测。每条自行编写的 XML 测试规则必须具有不同的、稳定的 `testDefName`；通用场景可用或少量技能场景通过，不等同于全部非 UI 类型已经完成。

实施约定：

1. 按第一批至第四批顺序实施。每批必须能独立构建、运行和验收，通过后单独提交，再进入下一批。
2. 每批提交同时包含本批实现、必要测试、相关说明更新和一份真实完成清单，不将四批代码积累成一次提交。
3. 可借用原版、DLC 和其他已安装模组的内容验证。实施时确认实际加载的 Def、依赖和游戏版本，记录测试对象；不为让工具验收通过而修改被测模组。
4. 首版以 RimWorld 1.7 为交付和实测后端。共用 CLI 不影响已有 1.6 功能，新增能力在未支持的后端明确返回不支持，不将本计划扩大成全面回迁。
5. 不使用电脑控制技能。通过 CLI、游戏原生执行接口和工具自身的场景/截图能力验证；图像可以直接读取工具生成的原图检查。
6. 日志、结果、截图和测试存档只使用工具正式生成的原始路径，以 `result.artifacts` 或 `error.details.artifacts` 定位，不另建证据目录，不复制、重定向或另存 stdout/stderr。
7. 用户要求的四份完成清单属于本次授权交付，只记录功能、验证结论和原始产物引用，不另写测试报告或复制证据。
8. 每批遇到未解决的工具缺陷，应修复并重新验证受影响部分。无法完成的验收项如实保留，不能通过放宽断言、隐藏异常或将未执行项目计为通过来结束本批。
9. 工具验收与被测模组结果分别判断。第三方真实缺陷可以作为正确识别失败的案例，但仍须另用机制明确的正例验证工具能力；不要求擅自修复第三方，也不能用模组失败代替尚未完成的工具验证。

## 2. 四批共同遵守的契约

| 项目 | 实施约定 |
| --- | --- |
| 外部输入 | 接受指定文件或文件夹；文件夹默认非递归枚举 `*.autotest.xml`；运行时固定文件清单、内容哈希及执行计划 |
| 自定义范围 | 全部既有非 UI 测试，包括战斗、技能、全部视图和实际功能执行；UI/功能混合用例按行为拆分，详见第 2.4 节及第 8.3 节 |
| XML 结构 | 首版 `schemaVersion="1"`，严格校验字段、类型、引用和重复 ID；禁用 DTD、外部实体及任意代码/反射调用 |
| 测试定义名 | 每条 XML 测试规则必填 `testDefName`，全部加载文件及 Suite 间唯一；与被测 DefName 和执行实例 caseId 分开，详见第 2.5 节 |
| 原生复用边界 | 仅直接接入角色生成、地图生成和游戏行为接口；外部 XML 解析、精确状态覆盖、场景执行与统计由工具实现，具体范围见第 2.3 节 |
| 角色配置 | 首版采用类似原生 PawnKind 的 XML 数据结构；以 Pawn 为生成基底，明确字段按配置处理，其余继承基底并按原生规则随机生成；支持 `inherit`、`patch`、`replace` |
| 时间 | 行为与 DPS 使用游戏 tick；停滞和超时使用实际时间；稳定 tick 不等同于轮询次数 |
| 技能执行 | 默认遵守原生资源、冷却和目标条件；显式调试干预独立记录，不继承旧技能测试的强制施放策略 |
| 执行与恢复 | 首批建立对象归属、取消、清理和恢复；串行执行，运行失败记录后继续后续测试项/运行批次，不因失败结果结束整个测试序列 |
| 替代覆盖 | 替代优先于批量上限；先保留有效替代，再处理其余候选与剩余额度。精确匹配 `packageId + defType + defName + caseType + variant`，实际执行与覆盖分别记录 |
| 回归报告 | Markdown 明细、Results、Screenshot Gallery 只列失败；机器结果保留全部；日志去重保留次数及关联用例 |
| 角色 XML | 暂定文件名 `temporary-test-pawn.xml`，直接位于最近自动测试项目的 `.tools/ProjectData`；跨重启保留，不部署、不上传 |
| 项目归属 | CLI 提供并持久化经验证的项目根目录和身份；不从日志路径、当前工作目录或游戏部署目录反推 |
| 游戏内普通测试 | 两个顶层 DebugAction：暂存测试角色、自动测试。第二项只运行内置普通测试；左右 TAB 批量选目标、统一选类别，首次无记录时类别全选；开始即关闭，重开恢复上次测试选择 |
| 手动产物 | “同类”指本次游戏进程启动内全部手动执行的测试；首次分配正式路径，本次启动后续全部追加；游戏重启后新建汇总，与自动测试分开 |
| 群战定位 | 独立数值评测，必须显式选择群战入口并指名测试名称/完整稳定 ID；不进入普通回归或全量扫描 |
| 群战地图 | 新建普通主地图，完成、取消或异常后丢弃；不使用口袋地图 |
| 群战阵营 | 默认生成两个互相敌对的临时阵营，分别承载双方；三方配置增加第三个敌对阵营，不增加召唤物或阵营转换的专门处理 |
| 群战结算 | 默认战斗 3 分钟模拟时间，可配置时长；一方全部倒下即判负，超时存活数较少方判负，同数平局 |
| 群战结果 | 分开记录对抗结局、执行状态和测量质量，不将落败、低 DPS 或数值差异判为 Bug 回归失败 |
| 展示与统计 | 群战完整数值、配装成功图、手动执行记录分别输出，不套用自动回归的失败明细过滤规则 |

外部回归入口采用 `test run --mode auto --scenario-path ...`，只跑外部回归时加 `--scenario-only`。群战采用独立的 `test run --mode groupcombat --scenario-path ... --test-name ...`。参数在所属批次实现并同步帮助文档，此处不表示现有 CLI 已经支持。

正式运行的测试输入可以由工具在项目 `.tools/ProjectData` 管理，解析器测试样例可以放在源码测试工程的 fixtures 中。它们属于功能输入，不属于测试证据；不得将场景定义写进被测模组的 Defs 或部署目录。既有日志和测试输出不迁移到 ProjectData。

### 2.1 首版角色结构与缺省生成

角色模板沿用 PawnKind 的字段组织习惯：普通属性写子节点，列表使用 `<li>`，区间使用原生的 `最小值~最大值`。工具使用自己定义的外部 `PawnTemplate` 数据契约及基底 PawnKind 引用，不将模板作为模组 Def 注册，也不把外部文件直接反序列化为完整的游戏内部类型。

首版字段至少覆盖：基底 PawnKind、race、性别与生成年龄、装备与服装的标签/预算/指定项、forcedTraits、skills、abilities，以及测试所需的明确装备、Hediff 和外观覆盖。原生已有的字段尽量保留名称和数值语义，测试扩展字段单独定义，第一批提交正式字段表及可运行示例。

```xml
<PawnTemplate id="temporaryPawn">
  <basePawnKind>Colonist</basePawnKind>
  <race>Human</race>
  <minGenerationAge>20</minGenerationAge>
  <maxGenerationAge>35</maxGenerationAge>
  <apparelTags>
    <li>IndustrialBasic</li>
  </apparelTags>
  <apparelMoney>350~600</apparelMoney>
  <skills>
    <li>
      <skill>Shooting</skill>
      <range>10~15</range>
    </li>
  </skills>
</PawnTemplate>
```

上例未指定性别、其他技能或具体装备时，由基底和原生生成规则补齐；写出范围的属性在指定范围内随机。暂存角色也是这种可部分定义的生成模板，不要求完整克隆全部模组内部状态。只要 Pawn 基底有效，未定义的字段不构成“角色不可用”。明确写错 Def、非法值或无法满足的显式约束仍按具体配置错误处理，不将它们静默改成别的值。

### 2.2 替代优先及批量额度

先解析有效 XML、常规候选和范围匹配信息，完成精确替代匹配后再施加批量额度。原生常规筛选未命中的合法 XML 场景仍保留为额外候选，不因不在常规范围内而直接丢弃。

执行顺序固定为：

1. 先执行本次范围内匹配成立的全部替代场景，移除它们承接的普通用例；替代场景不能被批量裁掉。
2. 将替代实际执行数量计入额度，再从其余范围内的常规/补充候选中补足。
3. 仍有剩余额度时，执行没有命中本次常规范围的合法 XML 场景，直至到达上限或候选耗尽。

额度按参数矩阵展开、执行去重后的物理 Case 计数；一个联合 Case 承接多个普通用例仍只占一个执行额度。若替代数量本身超过上限，仍保留全部替代，不再增加其他候选，并如实报告实际数量及超过上限的原因。未选中的有效 XML 记录批量原因，不计为执行成功或已覆盖。

| 上限 | 替代 Case 数 | 其他范围内候选数 | 范围外 XML 数 | 最终执行 |
| --- | --- | --- | --- | --- |
| 10 | 3 | 4 | 5 | 3 个替代 + 4 个范围内候选 + 3 个范围外 XML |
| 10 | 3 | 20 | 5 | 3 个替代 + 7 个范围内候选 |
| 2 | 3 | 4 | 1 | 保留全部 3 个替代，其他不执行 |

合法但不在本次常规范围内，与引用不存在的 Def、错误覆盖键是不同情况，后者仍报配置错误。上述规则用于引入 XML 的混合执行计划；没有外部 XML 时保留现有普通测试选择行为。

### 2.3 原生能力复用与自行实现的边界

用户已确认：只接入经过评估能够直接减少实现和维护成本的原生能力，不以复用数量为目标。首版新增原生接入限定为以下三类：

| 直接复用的能力 | 接入方式 | 工具仍需负责的内容 |
| --- | --- | --- |
| 角色生成 | 引用已加载的 PawnKindDef，通过 PawnGenerationRequest、PawnGenerator 正常生成，保留原生初始化、随机与模组回调 | 生成约束映射、明确状态覆盖、对象身份、阵营选择和生成后验证 |
| 地图生成 | 引用已加载的 MapGeneratorDef、GenStepDef，调用原生地图生成和卸载流程；分别适配口袋地图与普通主地图 | 场景预设、参数、环境验证、简单固定布局、对象归属与清理恢复 |
| 游戏行为 | 使用原生创建/生成物品、穿戴和装备、健康状态修改、死亡、原生攻击和技能施放接口，并沿用对应行为的原生合法性判定 | 动作参数、目标引用、精确修改策略、执行阶段记录、前后状态验证与异常处理 |

工具自行实现外部 XML 数据契约与解析、Def 名称解析和错误定位、模板覆盖、固定步骤与等待断言、测试筛选/替代/批量计划、角色 XML 持久化、手动会话、伤害账本、统计、显示和报告。共享契约与 CLI 静态校验不依赖游戏内部对象图；游戏侧适配器再将已经校验的输入映射到上述原生接口。

实现约束：

- PawnKind 风格保留熟悉的字段、列表与范围写法，不承诺兼容整套原生 Def XML、所有内部字段或任意 `Class`。外部文件不走完整的 DirectXmlToObject/全局 Def 交叉引用加载流程。
- 已加载的基底 Def 作为只读输入。单场临时生成配置与覆盖不得修改共享原 Def，避免影响其他单位和后续测试。
- 初始角色正常继承游戏已有的配装和 startingHediffs 等生成行为。工具不新增原生配装规则或 StartingHediff 的独立通用导入层；“仅替换帽子/武器”“修改已有 Hediff 严重度/指定部位”等由专用准备逻辑调用原生 API 并核对结果。
- 精确覆盖不重新运行会清空整套服装的原生服装生成流程，也不以 startingHediffs 跳过已有效果的行为代替显式修改。角色未定义的字段继续按原生规则生成。
- 简单地形、墙、掩体、出生位置由工具按坐标或矩形规则生成，调用原生摆放接口；首版不新增 PrefabDef 导入/导出或 LayoutDef/StructureLayoutDef/LayoutRoomDef 布局系统接入。
- 不接入 PawnGroupMaker 的点数/权重组队流程来实现固定人数群战。数量、编组和站位由工具控制，逐个调用原生角色生成与原生战斗行为。
- 不以 Scenario/ScenPart 或 QuestScriptDef/QuestNode 作为测试步骤、条件或生命周期基础，也不为少量筛选字段接入整套 ThingFilter。精确 Def/场景对象筛选由工具实现，技能目标合法性继续交给原生技能接口。
- 引用的已加载地图生成器若在内部使用 Prefab、布局或其他游戏系统，仍按其原生流程执行；上述边界限制的是工具新增的直接配置入口，不限制合法生成器的内部实现。
- 项目已有的操作记录、等待、截图和恢复组件仍可复用。现有角色/三视图准备服务中强制改玩家阵营、清空装备等策略应拆分或参数化，不能整段沿用到要求敌对阵营或保留全配装的场景。

本节确定四批的实现边界；未列为直接接入的原生系统不作为隐含交付项或验收前置条件。现有角色配置、固定场景和自定义已加载生成器等用户需求继续交付，使用工具自己的配置与准备逻辑完成。

本节限制原生系统的接入手段，不缩减全部非 UI 测试的自定义范围；缺少可直接复用的接口时，由工具实现对应的配置、准备和验证逻辑。

### 2.4 全部非 UI 测试的自定义范围

所有既有 Combat、View、Misc 非 UI 测试都须具备 XML 自定义能力，包括武器/炮塔/服装/各类 Pawn 战斗、技能、全部三视图及其他地图视图。配方生产、健康效果、尸体和普通 Thing 状态变化等实际功能也使用自定义场景，不因当前代码将其放在某个 UI 用例中而排除。

每类规则支持其适用的目标 Def 和实例参数、角色基底及覆盖、敌友/目标组、环境、步骤顺序、观察窗口、截图条件和成功判据。已有测试模块的固定行为仅作为缺省策略；显式 XML 条件应生效，不能只允许换一个 DefName 后仍执行完全固定的准备和判定。

UI 边界按实际检查内容划分：

- 信息卡、窗口、菜单、按钮和 Gizmo 界面交互不新增 XML 自定义支持，继续使用现有 UI 测试。
- 真正的配方执行、产物生成、资源消耗、健康变化及技能效果属于功能验证，即使现有 CaseType 名称含 `Ui`，其功能部分也须支持自定义。
- 角色、装备、植物、建筑、地形等截图/渲染测试属于 View，纳入自定义范围，不能将所有截图都归为被排除的 UI。
- 不删除既有 UI 自动或手动检查，也不通过功能场景成功宣称 UI 已通过；自定义功能场景不为取证额外依赖 Gizmo 等界面探针。

四类实体生成之外，配置还要支持相关 Def 引用和地图区域目标，例如地形区域、配方/工作台、发型/头型/体型、Gene/Xenotype。它们不需要被伪装成普通 Thing。所有类型的配置项、动作、判据、交付批次和独立验收见第 8.3 节。

### 2.5 测试规则的唯一 DefName

每个 XML 中可独立运行的 Case 代表一条测试规则，必须在其下填写 `<testDefName>`。该字段是外部测试系统的定义名，不需要写入模组本体或注册到游戏 Def 数据库。

| 身份 | 约定 |
| --- | --- |
| `testDefName` | XML 作者填写的必需、稳定测试定义名，建议含项目/模组及用途前缀；用于点名运行、结果归属、重跑和规则关联 |
| `targetDefName` / 目标列表 | 被测对象的游戏 DefName；单一目标和多个目标分别保留，Coverage 中的 `Target.defName` 仍指被承接的游戏定义 |
| `caseId` | 参数矩阵、变体、重复实验展开后的执行实例标识，同一次执行计划内唯一；关联所属 testDefName，跨运行以 runId + caseId 定位 |
| Suite ID、Case 的 `id` | 文件组织和局部引用标识，可继续保留，但不能代替必填 testDefName |
| `name` / 显示名 | 面向用户的可读名称，可以重复；涉及按显示名选择时必须唯一匹配 |

规则要求：

1. 全部参与加载的 XML 文件及 Suite 间按大小写不敏感比较 testDefName；缺失、空白或重复在执行前报错，并指出两处定义位置，不能仅按文件内或 Suite 内去重。
2. 同一游戏目标允许多条规则，每条 testDefName 必须不同。例如 `Axolotl_Move_AppliesHediff` 和 `Axolotl_Move_LandingView` 可同时针对 `Axolotl_SkillMove`。
3. 一条规则允许关联多个被测 Def，仍使用一个 testDefName；矩阵及重复实验产生不同 caseId，不以新随机测试名替代原规则身份。
4. 规则改文件名、移动目录或重复运行，不自动改变 testDefName；修改规则内容记录输入哈希，不能由时间戳/临时 GUID 生成持久定义名。
5. 注册、选择、执行去重、截图命名、日志和结果关联都应带上测试定义与实例身份，不能继续只用被测 DefName 作为自定义用例唯一键。
6. 群战规则也必须有 testDefName。`--test-name` 优先匹配该名，允许唯一显示名或原完整稳定 ID 定位；结果始终返回规范 testDefName，普通回归仍不得自动启动群战。
7. 游戏内入口合成的手动执行可以由工具按明确策略分配测试定义身份，再用 InvocationId/caseId 区分本次实例；不要求玩家手写 XML，但也不能用被测 DefName 混淆多个测试项目。

### 2.6 游戏内普通自动测试弹窗

第二个 DebugAction 为“自动测试”，点击后打开专用 UI 弹窗，形式与筛选体验参照刷物品弹窗 Dialog_DebugSupplies。它由玩家手动发起，但只执行内置普通测试，不加载或运行需要作者手写测试 XML 的自定义场景；群战保持独立入口，不接入本弹窗。顶层仍只有“暂存测试角色”和“自动测试”两个动作。

弹窗分左右两个 TAB/选择区：

| 区域 | 内容与操作 | 状态规则 |
| --- | --- | --- |
| 左 TAB：物品/目标 | 图标、名称、DefName、来源及多选框；支持名称/DefName/模组关键词搜索、模组和类型/分类筛选、第三方过滤、查看已选、全选当前筛选、清空选择 | 允许同时勾选多个目标；更改筛选和滚动不丢失已选目标；物品和非物品目标均在这里选择 |
| 右 TAB：测试类别 | 仅“战斗测试、UI 测试、三视图测试”三个大类，可展开并勾选细分小类；支持大类全选/取消、部分选中状态，以及类别总全选/清空 | 首次无记录时类别全选，重开恢复上次测试的类别；整批共用一套选择，不为各目标分别设模式 |
| 底部操作区 | 已选目标数、类别数、预计执行项、适用性/参数提示、暂存角色状态、开始测试和关闭/取消 | 勾选只改变配置；点击“开始测试”保存本次选择、提交批次并立即关闭弹窗，无第二次确认 |

目标数据覆盖内置测试所需的 Thing/建筑/Pawn 实例、PawnKindDef、AbilityDef、RecipeDef、HediffDef、TerrainDef、GeneDef、XenotypeDef、HairDef、HeadTypeDef、BodyTypeDef 等已加载游戏对象/定义。非物品目标通过左侧类型筛选选择。左侧没有外部测试 XML 路径、规则列表或 testDefName 选择器。

右侧的三大类是弹窗显示分组，固定映射如下，不改变现有程序内部 scope：

| 显示大类 | 支持的细分范围 |
| --- | --- |
| 战斗测试 | 内置炮塔、远程武器、近战武器、服装/护甲、动物、机械族、异族、技能；原 Misc 技能归这里。已有无需手写测试 XML 的独立功能可放在“功能验证”子组 |
| UI 测试 | 全部现有信息卡、窗口/账单及其他内置 UI 检查，按实际类型分别选择 |
| 三视图测试 | 内置角色/装备/生命阶段/外观/基因/异种三视图，以及植物生长、建筑、地形等其他视图；具备内置默认执行方式的整套配装展示也归这里 |

大类勾选影响该大类全部已交付子类，不受折叠或筛选影响；取消部分子类显示部分选中。首次没有历史选择时类别全选，之后重新打开恢复上一次实际提交测试的目标和类别，不重置全选。尚未交付能力明确禁用；不额外建立第四个大类，不因三视图名称排除其他视图。

原来混合 UI/功能的用例按所选子类执行：UI 子类只检查界面，功能子类才实际生产或验证效果，不因旧实现将两者写在一起而绕过选择或重复执行。

批量执行规则：

1. 左侧目标集与右侧统一类别集生成适用的目标—测试组合。多个物品使用同一套类别选择，不出现逐物品模式配置；不适用组合显示原因，不强行执行或记为通过。
2. 候选、类别和执行计划仅来自内置测试能力；不读取上次 CLI 的外部场景路径、规则缓存或补充/替代映射，不为目标自动匹配手写 XML 测试。
3. 暂存角色入口自动生成的 PawnTemplate XML 仍可作为普通测试的角色数据使用，不要求用户手写规则；它不提供测试 Steps/Success/Coverage，也不使本弹窗承担外部测试规则加载。
4. 底部显示实际可执行数量；没有目标、没有类别、没有适用组合或必需参数不满足时给出明确状态。显式选定的手动批次不被普通 auto 随机批量上限静默裁掉，也不自动变成全模组扫描。
5. 点击开始时保存并冻结目标、统一类别、角色数据和内置计划，分配 InvocationId，然后立即关闭配置弹窗。各任务独立 caseId，串行执行，需要角色时优先使用自动暂存数据。
6. 弹窗关闭即释放其配置暂停，进度显示不得暂停测试。运行中重新打开仍显示上次提交的选择，不重新强制暂停或修改正在执行的计划。
7. 全部调度使用真实执行能力并标为手动，不开启 autoTestEnabled、不复用自动 RunId、不发自动完成信号；保持忙碌提示、取消、清理和恢复。
8. 全部普通测试批次追加到本次 GameLaunchId 的同一 ManualSessionId 和正式路径，保留每个目标/类别的结果；不与 CLI 自动测试产物合并，不改写最近自动测试项目身份。
9. 测试项或运行批次失败时记录完整结果与错误，执行清理恢复，然后继续后续测试项及后续运行批次；不弹出必须人工确认才能继续的对话框，不把失败改成通过。这里的运行批次与四批代码实施验收分别处理。
10. 上次选择按稳定目标身份和类别标识保存，不使用列表行号；重开读取最近实际提交的测试选择。未开始就关闭的草稿不覆盖它，失效目标或类别明确标记，不以重置全部选择替代恢复；选择状态与每次启动新建的结果会话分开。

参照刷物品弹窗的视觉、筛选、多选和滚动方式，按需提取通用控件；测试候选目录、类别树和计划生成由测试功能实现，不直接复用只包含物资 ThingDef、数量和刷出行为的数据模型。

第三批交付这个普通测试专用弹窗及全部内置常规 UI/非 UI 类型的批量执行与验收。外部 XML 自定义能力和第四批独立数值评测按各自计划交付，不为本弹窗新增对应选择或调用路径。

## 4. 第一批：外部 XML 场景执行闭环

### 4.1 目标

用户指定一个外部 XML 后，能独立完成场景校验、唯一测试定义注册、四类实体及其他类型目标引用、角色配置、动作执行、效果验证、截图和清理。建立全部非 UI 类型共用的自定义契约和逐类清单，第一批即可运行基础场景，各类型适配按第 8.3 节在后续批次交付。

### 4.2 实现内容

1. 自行实现 XML 数据契约、解析和计划编译，覆盖 Requirements、Templates、Scene、Teams、Actors、目标引用、Steps、Success。角色字段按第 2.1 节组织，遵守第 2.3—2.5 节范围和身份规则；提交各非 UI 类型的字段/动作/判据清单、示例及文件/目录入口、输入冻结、错误定位。
2. CLI 先校验语法和静态引用，游戏加载后校验 Def、DLC、模组能力、身体部位及生成条件。未知字段和未支持能力明确报错，不静默丢弃。
3. 提供 Pawn、建筑、Thing、尸体的场景装配。尸体由完整 Pawn 经正常死亡产生，分别保留尸体与内层 Pawn 身份；分组生成具有稳定成员 ID。
4. 实现 PawnKind 原生生成及服装、武器、特性、工作技能、Hediff、Ability 的继承和覆盖。未定义项按基底/原生规则随机补齐；明确配置的字段应用后核对实际状态，缺少对应 tracker 或部位时报告具体约束问题，不将省略字段当成角色不可用。
5. 实现基础动作：摆放、装备和健康准备、原生攻击、原生施放、检查前置条件、基线、条件等待和截图。施放接受、开始、完成及效果出现分别记录。
6. 条件覆盖 All/Any/Not、any/all/count、当前满足/窗口内曾满足/持续满足，以及新增或移除 Hediff、Thing 创建/销毁、角色状态和尸体状态。空目标集合不通过，瞬时效果按 tick 或事件观察。
7. 使用现有口袋地图服务建立基础场景，显式处理视野、渲染和相机准备。不将“生成了图片文件”单独等同于画面或技能效果正确。
8. 从第一批建立统一状态机、对象归属和资源释放。准备异常、探针异常、断言超时均记录失败并清理，之后继续后续测试；取消仍按显式取消处理。复用十秒镜头恢复及 CLI 外部超时；游戏内恢复依赖主循环仍能运行，不将它视为主线程完全阻塞时的外部恢复机制。
9. 增加场景原始结果与失败分类，保持现有普通自动测试、日志去重和失败报告规则。外部场景首批先独立执行，不提前宣称替代任何普通用例。
10. 由 CLI 在自动测试正式开始时记录有效项目根目录、项目身份、游戏版本和运行标识，持久化供第三批使用；不能被单次配置恢复清掉。手动与群战入口不改写“最近自动测试项目”身份。
11. 实现必填 testDefName、跨文件/Suite 重复检查和规则注册，区分被测对象 DefName、局部 ID 与执行实例。改造自定义注册/去重/结果键，使同一目标的多条规则均保留；为后续矩阵、覆盖、手动和群战复用身份契约。

基础场景运行时遵守原生限制。现有技能模块中的冷却重置、次数补充及强制可用性补丁需要按执行来源隔离，防止外部场景和后续群战默认受到影响。

角色基底由原生生成，精确准备由本工具的小型服务完成。复用现有准备代码前检查其阵营、脱装和默认补齐策略，保证调用者能保留场景指定阵营及未修改的配装；不修改共享 PawnKindDef。

## 5. 第二批：全部非 UI 战斗/技能/功能适配与替代覆盖

### 5.1 目标

用户能够高度自定义全部非 UI 战斗、技能和实际功能执行，补充通用测试失败的内容，并按精确范围替代普通用例。交付第 8.3 节 C01—C08、C24—C27，不等待群战统计。

### 5.2 实现内容

1. 提供固定 actionId 注册、参数契约、目标类型和无交互执行适配。XML 只允许单体和地图坐标矩形选择，矩形限定本场景对象，支持敌人、友军及全部场景 Pawn 的过滤。
2. 支持在步骤中执行登记动作，例如资源准备、等待状态变化后的中途干预。记录实际目标、前后状态和异常；调试动作不能无记录地制造被归因于技能的效果。
3. 为已选真实技能增加必要的资源和状态适配，不向 XML 开放任意字段或方法。原生调试菜单存在不代表该动作已支持，需实际执行和后置验证。
4. 提供地图预设引用及允许的局部覆盖，包括开阔场、室内展示场、掩体/通道布局，支持已加载 MapGeneratorDef。简单布局由工具按坐标/矩形调用原生摆放接口实现，不增加独立 Prefab 或原生房间布局导入；校验地形、屋顶、天气、温度、光照、可达性、站位和生成器依赖。

### 7.3 对抗调度、伤害账本和统计

1. 默认创建两个互相敌对的临时阵营，分别设置双方单位；三方场景再增加第三个临时阵营并两两敌对。工具按明确数量、编组和站位逐个调用原生角色生成，不使用点数/权重组队代替固定人数。生成全部对象后同步开始，原生 AI 或统一攻击策略必须使动物等单位实际接敌。不增加专门的阵营转换处理或联盟规则。
2. 默认战斗时长 180 模拟秒，即 10800 ticks，允许 XML 自定义。一方全部倒下即判负，不默认等待额外复活窗口；到时比较双方当前场内存活数，少者判负，相等平局。死亡、逃离或移出场景不算仍站立，倒地活人计入超时存活数；同 tick 双方全部倒下判平局。另设实际时间上限处理卡死，不代替战斗模拟时长。
3. 在原生结算伤害入口建立精确在线累计，以引擎 DamageResult 为主口径。记录唯一事件身份、tick、施加者、受击者、队伍、伤害类型和武器。
4. 处理死亡时脱离地图、嵌套/反伤、多次同 tick 同额命中等情况。输出、承伤和分项账目可以核对，不能将日志文本去重用于伤害事件。
5. 同组、自伤、环境及未知来源与对敌直接伤害分开。护盾吸收、装甲损耗和生命伤害分别统计；未适配的持续伤害或直接健康修改标明覆盖限制，不能猜测伤害量或归给最近攻击者。召唤物的生成、阵营和行为由游戏处理，首版不新增召唤归属、召唤者贡献或专项转换适配。
6. 累计计数器不受证据环形缓冲区上限影响。详细事件采样不能改变汇总精度，数据质量和归属完整性必须可见。
7. 输出各单位、各方及三方伤害矩阵，以场景配置的临时阵营标识参战方。剩余数量区分站立、倒地、死亡、逃离和未知移除，不开发专门的阵营转换账本。
8. 主 DPS 使用共同的战斗窗口：累计对敌结算伤害 /（已推进 ticks / 60）。所有初始成员包括死亡、零输出和零承伤成员进入对应分布。
9. 各方及逐单位输出、DPS、承伤计算最高、最低、平均和中位数，最高/最低标出单位；中位数在原始精度上计算。额外的存活时间 DPS 必须另命名。
10. 支持明确列出的多个种子和双方位置交换，保留每场结果及跨场汇总，区分单场单位分布和跨场次分布。
11. 群战结果按名称完整输出，对抗输赢、执行完成度与测量质量分别记录。有限时或僵持结局仍可取得有效数值；程序异常和采集缺口明确列出。

三方配置沿用相同原则：全倒的一方判负并退出胜负竞争，其余方继续，直到仅剩一方或到达时限；超时按存活数排序，最高同数的方并列，低于最高者判负。默认不以无伤害提前结束，双方僵持将继续至指定时限。

### 7.4 屏幕显示

两方默认 A 左、B 右；三方保留两侧面板并在底部居中增加第三方面板。根据分辨率调整尺寸并支持必要的区域滚动，保证第三方的完整数据可查看。

每方面板必须包含：

- 方名，以及本方各自独立的累计输出 Top10、累计承伤 Top10 横向条形榜。
- 榜单单位的名称、图标/人类角色实际渲染图、累计量和存活状态；同指标跨方使用相同刻度。
- 当前场内存活数量最多的前五种单位，显示代表图、类型名称和 `X数量`。按 PawnKind 与明确的角色/配装模板编组，随机发型不拆组。
- 下方实时人均 DPS、总承伤及人均承伤，另列当前存活/初始数量。人均量以初始人数为分母，DPS 时间以已推进模拟 tick 为准。

人类图像来自实际生成且完成配装的角色；图像缓存复用，外观或装备变化时刷新。界面初始按 250 毫秒间隔更新排序和文字，账本继续精确随事件累计；暂停不改变 DPS 分母，结束后冻结。死亡单位的既有排行保留并标记，存活阵容数量只统计仍在场且活着的单位，倒地活人包含在内。

## 9. 完成清单与提交要求

每一份完成清单必须随对应批次代码提交，至少包含：

1. 批次范围、完成日期、验证时的源码基线和实际使用的游戏/工具版本。
2. 已完成的功能项及与本计划的对应关系；没有实现或没有验证的项目不得勾选完成。
3. 本批验收编号逐项记录：测试输入/目标、实际命令或游戏原生调用、预期、结果和结论。
4. 构建、纯逻辑检查、真实游戏检查及必要图像检查的实际结果，不预填测试数量。
5. 工具返回的运行标识及原始 `artifacts` 路径，必要时注明某路径缺失。清单不粘贴大量原始日志，不另存证据。
6. 预期负例、第三方缺陷、支持范围、未解决问题和对下一批的影响；工具失败不能只解释成模组问题。
7. 既有功能回归、路径隔离及清理恢复的验证结论。
8. 本批修改文件范围和提交说明。提交后在聊天报告最终提交哈希与清单路径，清单不编造自身尚未形成的提交哈希。
9. 本批负责的 C01—C29 矩阵行状态和对应测试定义/执行实例；类型未完成、未验证或参数仍被固定策略覆盖时如实列出，不能以其他类型通过抵消。
10. 第三批附 M01—M06 普通测试弹窗状态、类别映射及各内置 CaseType 调用记录、批量统一选择和来源隔离结论；不能以 XML 能通过 CLI 运行证明专用弹窗已经支持。

提交步骤为：实现与验证完成 → 核对原始结果 → 撰写本批完成清单 → 检查实际差异与必要空白检查 → 仅暂存本批文件 → 单独提交 → 报告提交哈希及验收结论 → 进入下一批。

保留用户和其他任务的无关修改，不使用全量暂存将其混入本批。无需为已授权的每批本地提交重复申请确认；推送或公开发布不属于本计划的交付步骤。
