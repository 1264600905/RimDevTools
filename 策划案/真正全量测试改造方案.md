# 真正全量测试改造方案

## 文档目标

这份文档不是在讨论“这次为什么没跑全”，而是在设计一套后续可持续使用的机制，保证：

1. 自动测试可以真正做到“全量”
2. 同一个 `defName` 在不同测试类型下可以重复出现，并且要被视为不同测试用例
3. 以后新增新的测试模块时，不会再次出现“表面上是全量，实际上只是被批次截断后的部分结果”

这里特别强调一条业务规则：

- `InfoCard` 测试和 `PocketMap` 测试即使目标是同一个 `ThingDef`
- 也必须视为 **两个不同测试类型**
- 不能因为 `defName` 相同就合并、去重或互相覆盖

例如：

- `Axolotl_BlackGoldFirearm`
  - `ItemInfoCard`
  - `RangedWeaponPocketMap`

这两个都应该独立存在、独立执行、独立统计、独立出报告。

## 当前问题的根因

当前实现里，全量测试不可靠，根因不止一个。

### 1. 发现目标和执行调度耦合在一起

现在 `AutoTestRunner.Initialize()` 会一边枚举目标，一边往不同队列里直接塞数据：

- `pendingItems`
- `pendingTurretDefs`
- `pendingRangedWeaponDefs`
- `pendingMeleeWeaponDefs`

然后立刻调用 `ApplyBatchLimit()`。

这意味着：

- 还没有形成完整“测试清单”
- 就已经开始裁剪队列

结果就是，当前系统只能保证“跑了一部分”，不能保证“已经发现了全部应测对象”。

### 2. 内容类共用一个总队列，容易互相饿死

现在以下内容都混在 `pendingItems`：

- `Building`
- `Item`
- `Terrain`
- `Recipe`
- `Hediff`

这会导致：

- 前面入队的类别吃光名额
- 后面的类别即使理论上支持，也可能完全进不了结果

### 3. 全局 batch limit 截断的是“测试集合”，不是“执行节奏”

当前 `autoTestBatchSize` 的语义是：

- 在发现完队列后，直接裁掉多余测试对象

这不是“分批执行”，而是“分批删除”。

对于真正的全量测试，`batch size` 应该只控制：

- 单次执行的节奏
- 单轮并发数量
- 是否拆成多批运行

而绝不能影响“全量清单本身”。

### 4. 结果模型没有显式区分“测试类型”

当前结果里主要靠：

- `Category`
- `DefName`

来区分记录。

这不够稳定，因为：

- `Item` 是一种内容分类
- `RangedWeapon` 是一种测试场景
- 两者不是同一维度

同一个 `defName` 在不同测试类型下的记录，现在只是“碰巧”没被覆盖，而不是在模型层明确支持。

### 5. XML-driven 目前更像“筛选器”，不像“规范化测试计划”

当前 `LogSyncAutoTestSpecDef` 更接近：

- allowlist 过滤规则
- 截图选项补充规则

但它还不是一套完整的“测试计划定义”。

缺点是：

- XML 模式很容易只留下少量命中对象
- 结果上看像“规范化测试完成”
- 实际上只是“只跑了命中的子集”

这不适合作为“真正全量测试”的长期基础。

## 设计目标

目标不是简单移除一个 `batch size`，而是建立一套稳定的测试架构。

### 核心目标

1. 先生成完整测试清单，再开始执行
2. 测试清单中的每一项都是“测试用例”，不是“Def”
3. 同一个 `defName` 可以在多个测试类型下生成多个测试用例
4. “全量模式”和“抽样模式”必须在语义上彻底分开
5. XML 规范化测试既能做全量约束，也能做定向覆盖，但两者不能混淆
6. 最终报告必须能证明“发现了多少、执行了多少、遗漏了多少”

## 推荐的新模型

### 一、引入统一的测试用例模型

建议新增一个显式的测试用例实体，例如：

```csharp
internal sealed class AutoTestCase
{
    public string CaseId;
    public string PackageId;
    public AutoTestCaseType CaseType;
    public AutoTestScope Scope;
    public string Category;
    public Def TargetDef;
    public string TargetDefName;
    public string TargetDefType;
    public string Label;
    public LogSyncAutoTestSpecDef SpecDef;
}
```

其中最关键的是 `CaseType`。

建议把它设计为“测试类型”，而不是“内容类型”。

例如：

```csharp
internal enum AutoTestCaseType
{
    BuildingInfoCard,
    ItemInfoCard,
    TerrainInfoCard,
    RecipeInfoCard,
    HediffInfoCard,
    TurretPocketMap,
    RangedWeaponPocketMap,
    MeleeWeaponPocketMap
}
```

以后如果新增模块，也继续往这里加，例如：

- `WeaponProjectileVisual`
- `BuildingPlacementValidation`
- `ApparelEquipFlow`
- `PawnInfoCard`

### 二、CaseId 必须唯一且包含测试类型

建议 `CaseId` 至少由以下字段组成：

- `packageId`
- `caseType`
- `targetDefName`

例如：

- `hentailoliteam.axolotl|ItemInfoCard|Axolotl_BlackGoldFirearm`
- `hentailoliteam.axolotl|RangedWeaponPocketMap|Axolotl_BlackGoldFirearm`

这样可以从模型层明确保证：

- 同一个 `defName` 的不同测试类型绝不会互相覆盖
- 结果、缓存、截图、重跑、失败追踪都可以精确定位到 case

## 真正全量测试的正确流程

建议把整个流程拆成 4 个阶段。

### 阶段 1：发现 Discovery

这个阶段只负责：

- 扫描所有支持类型
- 生成完整 `AutoTestCase` 清单

这个阶段不能做任何裁剪，也不能受 `batch size` 影响。

例如：

- 所有 `BuildingInfoCard` case 全量生成
- 所有 `ItemInfoCard` case 全量生成
- 所有 `RecipeInfoCard` case 全量生成
- 所有 `HediffInfoCard` case 全量生成
- 所有 `TurretPocketMap` case 全量生成
- 所有 `RangedWeaponPocketMap` case 全量生成
- 所有 `MeleeWeaponPocketMap` case 全量生成

发现结束后，系统必须得到一份完整 Manifest。

### 阶段 2：规范化过滤 Planning

这一阶段的输入是“完整 Manifest”，不是 Def 数据库。

这个阶段负责：

- 按当前运行模式筛选出本次要执行的 case
- 给 case 叠加截图、时间点、额外参数等测试配置

这里建议把 XML 的职责改成“作用于 Case”，而不是“直接阻止 Def 被发现”。

也就是说：

- 发现始终是完整的
- XML 只负责计划、修饰、显式排除或显式限定

### 阶段 3：调度 Execution

这一阶段才开始执行测试。

调度应面向 `AutoTestCase`，而不是面向原始 `ThingDef` / `RecipeDef`。

建议：

- 每种 `CaseType` 一个独立队列
- 每种 `CaseType` 可配置自己的并发上限
- `InfoCard` 类通常串行
- `PocketMap` 类可并发

### 阶段 4：收敛与校验 Verification

执行结束后，必须做一次完整校验：

- `discoveredCases`
- `plannedCases`
- `executedCases`
- `passedCases`
- `failedCases`
- `skippedCases`
- `missingCases`

对于真正的全量测试，必须满足：

- `plannedCases == executedCases + skippedCases`

如果不成立，这一轮测试即使没有报错，也必须标记为：

- `RunStatus = Incomplete`

## 对“全量模式”和“抽样模式”的重新定义

这是后续稳定性的关键。

### 模式 1：Full

语义：

- 跑完当前支持范围内的全部测试用例

要求：

- 不允许用全局 batch limit 直接裁剪 Case 集合
- 允许分批执行，但必须最终跑完整个 Manifest

### 模式 2：Targeted

语义：

- 只跑指定范围、指定类型、指定 defName 的测试用例

适用：

- 快速验证
- 定向回归
- 修 bug 时只测某几个目标

### 模式 3：Smoke / Quick

语义：

- 只验证运行环境、启动流程、模组加载、日志打通

不应被称为“全量”。

### 结论

后续命名上必须避免：

- “全量测试 + batch size=40”

因为这在语义上自相矛盾。

正确表达应为：

- `Full`：最终必须覆盖完整 Manifest
- `Targeted`：只跑指定子集
- `Quick`：只做启动验证

## 对 batch size 的正确改造

### 当前错误语义

当前 `autoTestBatchSize` 实际是在做：

- 发现后裁剪

这会直接破坏全量。

### 改造后的正确语义

建议改成以下两种之一。

#### 方案 A：`batch size` 只控制“单轮执行批次大小”

例如：

- Manifest 共有 312 个 case
- 本轮每次只执行 40 个
- 执行完一批后继续下一批
- 直到 312 个全部执行完

优点：

- 实现相对直观
- 保留了“分批降低压力”的能力

#### 方案 B：`batch size` 仅在 Targeted 模式下生效

即：

- `Full` 模式：忽略 batch 限制
- `Targeted` 模式：允许限制数量

如果目标是“保证后续都能全量”，我更推荐 **方案 B**，语义最清晰。

### 推荐做法

建议最终规则是：

- `Full` 模式：`batch size` 无效或强制视为 unlimited
- `Targeted` 模式：`batch size` 才允许生效

## 对 XML 规范化测试的改造建议

### 当前问题

现在 `LogSyncAutoTestSpecDef` 的匹配逻辑是：

- XML 驱动模式下，只有命中的对象才会进入测试

这适合“定向子集”，不适合“全量规范化”。

### 推荐的新语义：把 XML 分成两类职责

#### 1. 计划规则 Plan Rule

负责：

- 指定哪些测试类型启用
- 指定哪些 case 需要截图
- 指定哪些 projectile tick 生效
- 指定某类 case 的附加参数

但默认不阻止“全量发现”。

#### 2. 选择规则 Selection Rule

负责：

- 显式 include
- 显式 exclude

只有在 `Targeted` 模式下，才允许用 include 规则缩小测试集合。

### 建议保留现有 Def，但扩展字段语义

可以在 `LogSyncAutoTestSpecDef` 上增加类似字段：

- `testTypes`
- `selectionMode`
  - `Decorate`
  - `Include`
  - `Exclude`
- `priority`
- `captureOnFailure`
- `enabled`

其中最关键的是 `testTypes`。

当前 `scope` 不够，因为：

- `Content` 太粗
- 它无法区分 `ItemInfoCard` 和未来可能出现的 `ItemPocketMap`

### 建议的 XML 规则示例

```xml
<LogSyncMod.LogSyncAutoTestSpecDef>
  <defName>Axolotl_RangedVisualRule</defName>
  <selectionMode>Decorate</selectionMode>
  <testTypes>
    <li>RangedWeaponPocketMap</li>
  </testTypes>
  <defNames>
    <li>Axolotl_BlackGoldFirearm</li>
  </defNames>
  <captureScreenshots>true</captureScreenshots>
  <captureProjectileScreenshots>true</captureProjectileScreenshots>
  <projectileScreenshotTicks>
    <li>20</li>
    <li>40</li>
  </projectileScreenshotTicks>
</LogSyncMod.LogSyncAutoTestSpecDef>
```

这样它表达的是：

- 只给这个 case 类型叠加规则
- 不影响同 Def 的其他测试类型

## 调度层的推荐改造

### 一、按 `CaseType` 建独立队列

建议使用：

- `pendingBuildingInfoCases`
- `pendingItemInfoCases`
- `pendingTerrainInfoCases`
- `pendingRecipeInfoCases`
- `pendingHediffInfoCases`
- `pendingTurretPocketMapCases`
- `pendingRangedWeaponPocketMapCases`
- `pendingMeleeWeaponPocketMapCases`

或者更统一一点：

```csharp
Dictionary<AutoTestCaseType, Queue<AutoTestCase>>
```

这样做的好处：

- 不再有 `Recipe`、`Hediff` 被 `Building`、`Item` 挤掉的问题
- 每类测试的调度策略可以独立调整
- 以后新增模块不会继续往 `pendingItems` 里硬塞

### 二、调度与发现彻底分离

建议结构上拆成：

- `AutoTestDiscoveryService`
- `AutoTestPlanningService`
- `AutoTestScheduler`
- `AutoTestExecutor`
- `AutoTestReportWriter`

这样后续新增模块时，只要：

1. 增加新的 `CaseType`
2. 增加发现器
3. 增加执行器
4. 注册到统一调度器

而不是继续把逻辑堆到 `AutoTestRunner` 里。

## 结果模型必须升级

如果要长期保证“真正全量”，结果文件必须能表达“这到底是哪一种测试”。

### 建议新增字段

当前 `AutoTestResult` 至少补充：

- `CaseId`
- `CaseType`
- `Scope`
- `TargetDefName`
- `TargetDefType`
- `RunMode`
- `DiscoveredOrder`
- `PlannedOrder`

其中最重要的是：

- `CaseType`
- `CaseId`

### 为什么必须这样做

否则你永远会遇到这种歧义：

- `Axolotl_BlackGoldFirearm` 到底是 Item 测过了，还是 RangedWeapon 测过了？
- 同一个截图是 InfoCard 的，还是 PocketMap 的？
- 同一个 def 的失败，究竟是哪一类失败？

模型里不明确，报表就永远不可信。

## 报告层必须增加“完整性证明”

建议每次运行除了 `_Result.json` 和 `_Report.md`，再额外输出一份 Manifest 或 Summary。

例如：

- `_Manifest.json`

内容包括：

- 每种 `CaseType` 发现数
- 每种 `CaseType` 计划执行数
- 每种 `CaseType` 实际执行数
- 每种 `CaseType` 通过、失败、跳过、缺失数

### 报告必须能直接回答的问题

1. 这次到底发现了多少个应测 case
2. 本次是否是全量模式
3. 哪些 case 没跑到
4. 哪些 case 被跳过
5. 哪些 case 是重复 def 但不同测试类型

### 建议在 Markdown 顶部增加

- `RunMode: Full / Targeted / Quick`
- `ManifestDiscovered: N`
- `ManifestPlanned: N`
- `ManifestExecuted: N`
- `ManifestMissing: N`
- `Completeness: Complete / Incomplete`

如果是 `Full` 模式且 `Missing > 0`，报告标题就应该直接标红为：

- `Full Auto Test Report (Incomplete)`

## run_test.py 的配套改造建议

脚本层也要同步改，否则用户还是会误触发“假全量”。

### 1. 显式区分运行模式

建议脚本层命令行明确支持：

- `--runner-mode full`
- `--runner-mode targeted`
- `--runner-mode quick`
- `--runner-mode manual`

不要再让“有没有传 packageId / scope / xml”去隐式推断“是不是全量”。

### 2. Full 模式下禁止裁剪

脚本在 Full 模式下应强制：

- 清空 `autoTestBatchSize`
- 或写入 `0 / unlimited`
- 并在启动前打印提示：
  - `Full mode ignores batch size`

### 3. 结束后校验完整性

脚本应在读取结果文件后检查：

- 本次是否 `RunMode = Full`
- 是否 `Completeness = Complete`

如果不是，脚本退出码应为失败。

这样 CI、批量验证、人工回归都能一眼发现“其实没跑完”。

## 推荐的实施顺序

为了风险可控，建议按下面顺序改。

### 第一步：先引入 `CaseType` 和 `CaseId`

目标：

- 不改变现有测试逻辑
- 先让结果模型和报告模型能表达“同一 Def 的不同测试类型”

这是最小成本、收益最大的第一步。

### 第二步：引入 Discovery Manifest

目标：

- 在真正执行前先生成完整 case 清单
- 把“发现总数”和“执行总数”从根上分离

这一步完成后，就能直接证明：

- 这次到底是不是全量

### 第三步：重写 batch 语义

目标：

- Full 模式不再裁剪 Manifest
- Targeted 模式才允许限制数量

这一步完成后，当前“全量其实只跑了前 40 条”的问题就会消失。

### 第四步：把 XML 从“硬筛选”改成“计划规则”

目标：

- XML 规范化测试可以继续存在
- 但默认不再破坏全量发现

需要子集时，再明确切到 Targeted 模式。

### 第五步：拆分调度器和执行器

目标：

- 为后续新增测试模块留出清晰扩展点
- 避免 `AutoTestRunner` 再次膨胀

## 最终推荐方案

如果要一句话概括真正的解决方案，那就是：

- **把“测试对象”从 Def 升级为 Case**
- **把“全量”定义为完整 Manifest 的全覆盖**
- **把 `InfoCard`、`PocketMap` 等不同场景显式建成不同 CaseType**
- **把 batch limit 从“裁剪集合”改成“控制执行节奏”**
- **把 XML 从“直接删目标”改成“规范化计划与配置”**

只有这样，后续无论是：

- 信息卡测试
- 炮塔口袋地图测试
- 远程武器测试
- 近战武器测试
- 未来的新模块

都能稳定接入同一套真正的全量测试体系。

## 对本项目的直接结论

对于你现在这个项目，我的明确建议是：

1. 不要再把“Def 是否重复”当成去重依据，去重要以 `CaseType + DefName` 为核心
2. 不要再让 `Full` 模式受 `autoTestBatchSize` 影响
3. 不要再让 `Building / Item / Terrain / Recipe / Hediff` 混用一个总队列
4. XML 规范化测试后续应默认服务于“全量计划”，而不是默认变成“只跑子集”
5. 报告必须能证明本次是否完整，否则“全量测试”四个字没有可信度

这套方案落地后，才算真正解决“如何修改实现真正的全量测试，并且保证后续测试都能全量测试”。
