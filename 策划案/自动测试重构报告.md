# 自动测试重构报告

## 1. 本轮重构目标

本轮重构的核心目标有两项：

1. 让自动测试具备“真正全量”的可证明执行能力，不再被旧的 `batch size` 行为误截断。
2. 把截图逻辑与口袋地图生命周期从巨型运行器中抽离成可复用模块，为后续继续扩展新的测试类型打基础。

本次工作没有试图一步把所有自动测试彻底插件化，而是优先完成“可运行、可统计、可扩展”的第一阶段重构落地。

## 2. 已完成的结构性改造

### 2.1 全量测试清单化

已引入统一的测试清单与结果标识模型，核心变化如下：

- 为每条测试结果增加稳定的 `CaseType`、`CaseId`、`Scope`。
- 执行前先生成完整 `Manifest`，再按清单执行测试。
- 结果输出增加完整性字段：
  - `runMode`
  - `completeness`
  - `manifestDiscovered`
  - `manifestPlanned`
  - `manifestExecuted`
  - `manifestMissing`
- 新增 `Manifest.json` 输出，便于后续校验“发现了多少 Def、计划执行多少、实际执行多少、漏了多少”。

这一步解决了此前“看起来跑完了，但实际上只跑了部分内容”的问题。

### 2.2 Full 模式不再被 batch size 截断

旧逻辑里，自动测试存在被 `batch size` 意外影响的情况。现在已改为：

- 当运行模式是自动测试且范围为 `All` 时，执行器直接跳过批量截断逻辑。
- `Targeted` 和 `Quick` 仍保留快速运行能力。

这一步是“真正全量测试”成立的关键前提。

### 2.3 运行器按模块拆分

原先超大体积的 `AutoTestRunner.cs` 已开始按测试类型拆分，当前已落地以下模块：

- `AutoTestRunner.ContentModule.cs`
- `AutoTestRunner.InfoCardModule.cs`
- `AutoTestRunner.TurretModule.cs`
- `AutoTestRunner.RangedWeaponModule.cs`
- `AutoTestRunner.MeleeWeaponModule.cs`
- `AutoTestModels.cs`

当前仍保留 `AutoTestRunner.cs` 作为总调度入口，但具体逻辑已经明显下沉到子模块，后续继续扩展新测试类型时，不必再把所有逻辑堆回单文件。

### 2.4 截图服务第一阶段模块化

已新增统一截图配置与服务入口：

- `AutoTestScreenshotProfiles.cs`
- `AutoTestScreenshotService.cs`

目前已经实现：

- 使用 `AutoTestScreenshotProfile` 统一描述不同测试场景的截图参数。
- 使用 `AutoTestScreenshotRequest` 统一描述单次截图请求。
- 炮塔、远程、近战、失败截图、动作截图开始通过统一入口发起，而不是各模块分别手写截图逻辑。

这一步没有完全做成“所有截图策略都可热插拔”，但已经完成了第一层解耦。后续若新增信息卡、口袋地图、射弹、失败态等特殊截图，只需要扩展 profile/request/service，而不必在每个测试模块重复实现。

### 2.5 口袋地图生命周期服务第一阶段模块化

已新增：

- `AutoTestPocketMapService.cs`

当前已统一处理：

- 口袋地图创建
- 口袋地图注册
- 基础销毁流程

炮塔、远程武器、近战武器三类口袋地图测试，已经开始通过统一服务管理生命周期，而不是各自直接散落操作地图对象。

### 2.6 InfoCard 自动关闭稳定性修复

在全量回归中，发现两个建筑存在 `InfoCard` 关闭超时。当前已补上关闭回退逻辑：

- 正常先走关闭按钮请求。
- 超过一半关闭等待窗口仍未消失时，执行 `ForceClose()` 回退。
- 回归后，这两个原本失败的建筑已经定向复测通过。

## 5. 当前剩余已知问题

当前全量回归还剩 1 个失败案例：

- `Axolotl_VastSeaCelestialWhaleCannon`
- `CaseType = RangedWeaponPocketMap`
- `Status = failed_no_damage`

已知现象：

- 日志中持续出现 `AttackVerbUnavailable=True`
- 该武器的 Def 明确声明：
  - `canTargetPawns = false`
  - `canTargetLocations = true`
  - `canTargetBuildings = true`

这说明它不是普通的“直射打 pawn”型远程武器，而是“地点/区域打击”型武器。当前远程口袋地图测试主流程还是按“攻击 pawn”建模，因此这个失败更像是“测试场景兼容性缺口”，而不是框架整体失效。

也就是说：

- 当前全量覆盖与统计框架已经成立。
- 剩余问题主要是个别武器类型的场景适配。

## 6. 这轮重构解决了什么

本轮重构已经明确解决以下问题：

- 解决了“全量测试不是真全量”的统计不透明问题。
- 解决了 `Full` 模式被 `batch size` 误截断的问题。
- 解决了结果模型缺乏稳定 case 标识的问题。
- 解决了截图逻辑过度散落、难以继续扩展的问题。
- 解决了口袋地图创建/销毁职责分散的问题。
- 解决了部分 `InfoCard` 自动关闭不稳定的问题。

## 7. 尚未完全完成的部分

虽然本轮已经完成第一阶段重构落地，但仍有以下后续工作值得继续推进：

1. 远程武器测试需要加入“地点炮击型武器”分支。
2. 截图服务还可以继续下沉“镜头聚焦策略”，把目前各模块中的 focus 细节进一步抽象出来。
3. 口袋地图还可以继续抽象出场景模板接口，让炮塔、远程、近战、未来新场景共享更多基础设施。
4. 结果报告可以继续增加“按分类/按 CaseType/按失败原因”的聚合摘要。

## 8. 结论

本轮重构已经完成了自动测试系统从“脚本式堆叠”向“清单化执行 + 模块化基础设施”过渡的第一阶段目标。

当前系统已经具备以下能力：

- 可以证明是否真正全量执行。
- 可以区分同一 Def 在不同测试类型下的独立测试记录。
- 可以统一输出结构化结果与截图归档。
- 可以在新增测试类型时复用截图与口袋地图基础设施。

在此基础上，后续继续补齐个别武器/特殊场景兼容时，不需要再推翻本轮重构成果，只需在现有模块边界内继续扩展即可。
