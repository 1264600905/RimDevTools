# 截图与口袋地图模块化改造方案

## 文档目的

这份文档专门讨论两件事：

1. 把当前自动测试里的截图逻辑拆成真正可复用的独立模块
2. 把当前炮塔 / 远程武器 / 近战武器反复使用的口袋地图机制拆成高扩展性的独立模块

目标不是简单“整理一下代码”，而是为后续更多测试类型提前铺路。因为从现在的演进方向看，后面很可能继续增加：

- 新的口袋地图战斗测试
- 新的投射物表现测试
- 新的失败截图 / 诊断截图
- 新的 UI 类截图
- 新的基于口袋地图的流程测试

如果这两部分不先模块化，后续每加一种测试，`AutoTestRunner` 就会继续膨胀。

## 当前现状总结

### 一、截图逻辑目前只“部分独立”

当前项目里已经有：

- `AutoTestScreenshotService.cs`

但它现在独立出来的其实只有：

- 文件名生成
- 截图落盘
- 标题叠字 overlay
- 结果对象 `ScreenshotPath / ScreenshotPaths` 的回填

真正决定截图行为的关键逻辑仍然散落在 `AutoTestRunner` 和各测试模块里：

- 什么时候截图
- 截图前是否切地图
- 相机应该看哪里
- rootSize 用多少
- 是否看全图
- 是否看炮塔与敌人中点
- 是否看近战动作点
- 失败截图和通过截图是否用同一套参数
- 投射物截图何时触发、如何判定命中屏幕中心

这些能力目前都没有被抽象成统一接口。

### 二、截图参数目前是硬编码常量 + 分散函数

当前 `AutoTestRunner.cs` 里存在大量直接影响截图行为的常量和函数，例如：

- `TurretScreenshotRangeScale`
- `RangedWeaponScreenshotRangeScale`
- `TurretScreenshotMinRootSize`
- `TurretScreenshotMaxRootSize`
- `TurretScreenshotCellMargin`
- `TurretScreenshotCameraPlusMinRootSize`
- `TurretScreenshotCameraPlusMaxRootSize`
- `TurretScreenshotCameraPlusCellMargin`

以及大量按场景分开的聚焦函数：

- `FocusTurretScreenshotMap`
- `FocusRangedWeaponScreenshotMap`
- `FocusMeleeWeaponScreenshotMap`
- `FocusMeleeAction`
- `FocusPocketMapOverview`
- `TryResolveTurretScreenshotView`
- `TryResolveRangedWeaponScreenshotView`
- `TryResolveMeleeWeaponScreenshotView`
- 投射物中心判定与聚焦相关逻辑

这意味着：

- 截图参数虽然“已经支持不同场景不同数值”
- 但这种支持是靠硬编码复制出来的
- 不是通过统一配置和统一接口实现的

### 三、口袋地图机制目前是“功能重复”而不是“能力复用”

炮塔、远程武器、近战武器三个模块里，都有一套非常相似的流程：

- 创建 `PocketMapParent`
- 设置 `sourceMap`
- 设置 `mapGenerator`
- `MapGenerator.GenerateMap(...)`
- 注册到 `Find.World.pocketMaps`
- 异常时销毁
- 成功后保存在 session
- 结束时调用 `PocketMapUtility.DestroyPocketMap(...)`

这三套代码结构极其接近，但没有共用一个统一的口袋地图服务。

所以现在的问题不是“不能复用”，而是：

- 每新增一个口袋地图测试类型
- 都要再复制一套创建 / 注册 / 清理 / 切图 / 相机 / 截图收尾逻辑

### 四、截图和口袋地图的职责边界还不清晰

当前很多逻辑混在一起：

- 口袋地图测试决定何时截图
- 同时也决定如何摆镜头
- 同时也直接操作相机
- 同时也处理失败截图目录
- 同时也做投射物截图时机计算

这会导致两个问题：

1. 截图能力无法单独复用
2. 口袋地图能力也无法独立扩展

## 改造目标

### 目标 1：截图成为真正独立的基础模块

期望效果是：

- “我现在要截图”时，只需要发起一个截图请求
- 不需要测试模块自己拼文件名、自己落盘、自己写 overlay、自己处理结果路径
- 不同测试类型可以传入不同截图参数

### 目标 2：口袋地图成为真正独立的测试场景模块

期望效果是：

- “我现在要开一个口袋地图测试场景”时，只需要声明场景模板和布置逻辑
- 不需要每个测试模块重复写地图创建、注册、销毁、切图、异常清理

### 目标 3：截图参数可配置、可扩展、可按测试类型分层覆盖

必须支持：

- 炮塔截图参数
- 远程武器截图参数
- 近战武器截图参数
- 失败截图参数
- 动作截图参数
- 投射物截图参数
- 未来新测试类型的专用参数

### 目标 4：未来新增测试时不再复制代码

例如以后新增：

- 爆炸物武器口袋地图测试
- 法术投射物口袋地图测试
- 多单位围攻口袋地图测试
- 建筑触发型口袋地图测试

只需要：

1. 定义新测试场景
2. 选择合适截图预设
3. 编写布置 / 判定逻辑

而不是重新复制一大段相机和地图管理代码。

## 建议的模块拆分

## 一、截图系统拆分方案

建议把截图相关能力拆成 4 层。

### 第一层：截图请求模型

建议新增一个明确的截图请求实体，例如：

```csharp
internal sealed class AutoTestScreenshotRequest
{
    public AutoTestResult Result;
    public string StageSuffix;
    public bool Force;
    public bool AllowCapture;
    public string RelativeSubdirectory;
    public AutoTestScreenshotProfile Profile;
    public Action Prepare;
    public Func<bool> Guard;
}
```

这个对象的职责是：

- 声明“要拍什么”
- 声明“用哪套参数”
- 声明“截图前如何准备”
- 声明“截图前的守卫条件是否满足”

这样测试模块只需要构造请求，不再直接操作落盘细节。

### 第二层：截图配置模型

建议新增一个统一的截图配置结构，例如：

```csharp
internal sealed class AutoTestScreenshotProfile
{
    public string ProfileId;
    public AutoTestCameraMode CameraMode;
    public float RangeScale;
    public float MinRootSize;
    public float MaxRootSize;
    public float CellMargin;
    public float CameraPlusMinRootSize;
    public float CameraPlusMaxRootSize;
    public float CameraPlusCellMargin;
    public bool UseOverviewOnFailure;
    public bool DrawOverlay;
    public int OverlayFrames;
}
```

这层的意义在于：

- 不同测试场景不再依赖散落常量
- 所有截图参数都可收敛到统一配置对象

### 第三层：相机聚焦策略

建议把“如何摆镜头”独立成策略接口，而不是继续在 `AutoTestRunner` 里堆函数。

例如：

```csharp
internal interface IAutoTestCameraStrategy
{
    bool TryResolveView(AutoTestCameraContext context, out Vector3 rootPos, out float rootSize);
}
```

建议最少拆出这些策略：

- `PocketMapOverviewCameraStrategy`
- `TurretEngagementCameraStrategy`
- `RangedWeaponEngagementCameraStrategy`
- `MeleeWeaponEngagementCameraStrategy`
- `MeleeActionCameraStrategy`
- `ProjectileCenterCameraStrategy`

这样之后如果要增加新场景，只需要新增一个策略，不必改公共截图服务。

### 第四层：统一截图执行器

建议把现有 `AutoTestScreenshotService` 升级成真正的统一入口，例如：

- `AutoTestScreenshotManager`

它统一负责：

- 检查 guard
- 调用 prepare
- 请求 overlay
- 生成文件名
- 落盘
- 更新 `ScreenshotPath / ScreenshotPaths`
- 写入 notes
- 失败归档到 `fail`

这样测试模块最终只需要：

- 发起一个 `Capture(request)`

## 二、截图参数的推荐组织方式

### 建议不要继续靠分散常量

当前这些值：

- `TurretScreenshotRangeScale`
- `RangedWeaponScreenshotRangeScale`
- 以及各种 min/max/cellMargin

已经说明项目实际上需要“多套截图参数预设”。

所以推荐改成显式的 Profile 注册表，例如：

```csharp
internal static class AutoTestScreenshotProfiles
{
    public static readonly AutoTestScreenshotProfile TurretPrimary = ...;
    public static readonly AutoTestScreenshotProfile TurretFailure = ...;
    public static readonly AutoTestScreenshotProfile RangedPrimary = ...;
    public static readonly AutoTestScreenshotProfile RangedFailure = ...;
    public static readonly AutoTestScreenshotProfile MeleePrimary = ...;
    public static readonly AutoTestScreenshotProfile MeleeAction = ...;
    public static readonly AutoTestScreenshotProfile PocketMapOverview = ...;
}
```

### 配置覆盖层级建议

后续建议支持 3 层覆盖：

1. 系统默认值
2. 测试类型默认 Profile
3. XML 或 case 级覆盖

例如：

- 炮塔默认用 `TurretPrimary`
- 某个炮塔 spec 里可覆盖 `RangeScale`
- 某个特定阶段还能再临时覆盖 `FocusRootPos / FocusRootSize`

这样既保留统一性，也保留精细调参能力。

## 三、口袋地图系统拆分方案

建议把口袋地图能力拆成 3 层。

### 第一层：口袋地图生命周期服务

建议新增：

- `AutoTestPocketMapService`

统一负责：

- 创建 `PocketMapParent`
- 设置 `sourceMap`
- 设置 `mapGenerator`
- 调用 `MapGenerator.GenerateMap`
- 注册到 `Find.World.pocketMaps`
- 地图存在性检查
- 清理与销毁
- 异常兜底

建议对外只暴露非常清晰的接口，例如：

```csharp
AutoTestPocketMapHandle Create(AutoTestPocketMapRequest request);
void Destroy(AutoTestPocketMapHandle handle);
bool IsAlive(AutoTestPocketMapHandle handle);
```

### 第二层：口袋地图场景模板

仅有“创建地图”还不够，后续真正会复用的是“场景模板”。

建议新增一个场景模板层，例如：

```csharp
internal interface IPocketMapScenario
{
    string ScenarioId { get; }
    IntVec3 MapSize { get; }
    void PrepareTerrain(Map map);
    void SpawnActors(Map map, AutoTestPocketMapContext context);
    void SpawnStructures(Map map, AutoTestPocketMapContext context);
    void SpawnHazards(Map map, AutoTestPocketMapContext context);
}
```

这样不同测试类型只需实现不同场景模板：

- `TurretPocketMapScenario`
- `RangedWeaponPocketMapScenario`
- `MeleeWeaponPocketMapScenario`
- 未来的 `ExplosiveWeaponPocketMapScenario`

### 第三层：口袋地图会话控制器

建议再往上加一层：

- `PocketMapSessionController`

负责：

- 会话状态推进
- 统一超时
- 首次伤害 / 首次击倒 / 首次击杀判定
- 地图关闭时机
- 截图宽限期
- 清理顺序

这一层把“场景”与“测试判定”彻底分开。

## 四、口袋地图上下文模型建议

现在三个测试模块都各自维护了自己的 session 类型：

- `TurretTestSession`
- `RangedWeaponTestSession`
- `MeleeWeaponTestSession`

这个方向没问题，但建议把共通字段再抽出一个共享基类或上下文对象。

例如：

```csharp
internal abstract class PocketMapTestSessionBase
{
    public AutoTestResult Result;
    public PocketMapParent Parent;
    public Map TestMap;
    public bool AllowScreenshots;
    public bool CaptureProjectileScreenshots;
    public List<int> ProjectileScreenshotTicks;
    public int CreatedTick;
    public int FirstDamageTick;
    public int FirstDownOrKillTick;
}
```

这样能减少：

- 地图引用
- 截图允许标记
- projectile tick 列表
- 关闭时机字段

等重复状态的复制。

## 五、截图系统与口袋地图系统之间的正确边界

这部分必须提前定义清楚，否则后面还会重新耦合。

### 口袋地图模块应该负责什么

- 地图创建与销毁
- 场景布置
- 测试对象生成
- 战斗事件监听
- 什么时候需要截图
- 给截图系统提供上下文

### 截图模块应该负责什么

- 相机切换与准备
- 相机参数选择
- overlay
- 文件命名
- 路径归档
- 调用 `ScreenCapture`
- 回填结果对象

### 不应该再发生的事

后续不应再让测试模块自己做这些事：

- 直接拼截图路径
- 直接决定“失败截图写入 fail 目录”这种底层行为
- 直接散落一组新的相机常量
- 直接调用 `ScreenCapture.CaptureScreenshot`

## 六、推荐的新调用方式

改造完成后，理想用法应接近下面这种形式。

### 示例：炮塔普通截图

```csharp
screenshotManager.Capture(new AutoTestScreenshotRequest
{
    Result = session.Result,
    StageSuffix = "projectile_center_t20",
    Force = false,
    AllowCapture = session.AllowScreenshots,
    Profile = AutoTestScreenshotProfiles.TurretPrimary,
    Prepare = () => cameraCoordinator.Focus(session, AutoTestCameraIntent.TurretPrimary),
    Guard = () => pocketMapService.IsAlive(session.PocketMapHandle)
});
```

### 示例：失败全图截图

```csharp
screenshotManager.Capture(new AutoTestScreenshotRequest
{
    Result = session.Result,
    StageSuffix = "failed",
    Force = true,
    AllowCapture = true,
    RelativeSubdirectory = "fail",
    Profile = AutoTestScreenshotProfiles.PocketMapOverview,
    Prepare = () => cameraCoordinator.Focus(session, AutoTestCameraIntent.PocketMapOverview),
    Guard = () => pocketMapService.IsAlive(session.PocketMapHandle)
});
```

这样截图模块和地图模块之间的边界会非常清晰。

## 七、对不同测试场景的参数支持要求

后续截图参数至少要支持下面这些维度。

### 炮塔测试

- 中心点取炮塔与目标中点
- rootSize 比远程武器更宽
- 失败截图默认使用口袋地图全图
- 可独立控制投射物截图参数

### 远程武器测试

- 中心点取射手与目标中点
- 不要因为抛射武器的弹道高度导致镜头跟着弹体漂移
- 更适合用固定视图 + 投射物 x 轴判定

### 近战武器测试

- 最终截图与动作截图应该是两套不同 profile
- 动作截图应聚焦近战接敌区域
- 最终截图更适合展示交战后的整体状态

### 失败截图

- 应与对应测试类型的主截图参数一致或近似
- 不应随意退回到一套完全不同的通用参数
- 但仍允许切换为 overview profile

## 八、推荐实施顺序

为了降低风险，建议按下面顺序重构。

### 第一步：只抽截图请求和截图配置

先不改场景逻辑，只把：

- 文件命名
- overlay
- 截图落盘
- 结果回填
- `fail` 归档

收敛到统一的截图请求入口。

这样可以先把“截图怎么拍”从“测试怎么跑”里分离出来。

### 第二步：抽相机聚焦策略

把 `FocusTurretScreenshotMap`、`FocusRangedWeaponScreenshotMap`、`FocusMeleeWeaponScreenshotMap` 等函数收拢成相机策略模块。

这一步完成后，不同测试类型的截图参数就真正可配置了。

### 第三步：抽口袋地图生命周期服务

先统一：

- 创建
- 注册
- 存活检查
- 销毁
- 异常清理

不急着一次性抽掉所有场景布置。

### 第四步：抽口袋地图场景模板

等生命周期稳定后，再把：

- 地形清理
- 建筑生成
- 单位生成
- 特殊环境布置

收敛成场景模板。

### 第五步：抽口袋地图会话控制器

最后再把：

- 首伤判定
- 首杀判定
- 截图宽限期
- 关闭时机

这类战斗流程控制上移到统一控制器。

## 九、最终建议

如果要一句话概括这次建议，就是：

- **截图模块要从“落盘工具”升级为“完整截图能力模块”**
- **口袋地图模块要从“三套重复实现”升级为“统一场景基础设施”**

具体来说，推荐最终形成下面这组职责清晰的模块：

- `AutoTestScreenshotManager`
- `AutoTestScreenshotProfiles`
- `AutoTestCameraCoordinator`
- `AutoTestPocketMapService`
- `IPocketMapScenario`
- `PocketMapTestSessionBase`

这样后续无论新增多少测试类型，都可以做到：

1. 通过统一口袋地图服务创建测试场景
2. 通过统一截图模块请求截图
3. 为不同测试类型单独配置截图参数
4. 不再把新逻辑继续堆进 `AutoTestRunner`

## 对当前项目的直接结论

目前项目已经证明：

- 你们的截图需求不是单一截图，而是多场景、多参数、多阶段截图
- 你们的口袋地图需求也不是单一炮塔测试，而是一个会被大量复用的测试场景系统

因此这两部分都已经到了必须“基础设施化”的阶段，继续靠在各测试模块里复制逻辑，会越来越难维护，也越来越难保证不同测试之间的行为一致性。
