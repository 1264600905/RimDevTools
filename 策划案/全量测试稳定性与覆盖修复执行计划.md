# 全量测试稳定性与覆盖修复执行计划

## 背景

本轮全量测试暴露出 4 个必须优先处理的问题：

1. 测试过程中如果出现袭击、重大事件或其他自动暂停源，游戏会被暂停，自动测试被打断。
2. 自动测试没有统一强制到 2 倍速，导致整轮回归耗时偏长。
3. 口袋地图并发数量虽然已有节流，但当前是硬编码，且不是统一可配置。
4. 三视图测试在 `All` 范围下被跳过，导致当前“全量测试”并不是真正的全量。

这 4 个问题里，三视图漏跑是覆盖率 bug，暂停和速度是稳定性问题，并发上限是资源调度问题。它们都属于自动测试运行时控制层，而不是单个测试类型自身逻辑的问题。

## 当前源码结论

### 1. 三视图被 `All` 范围漏掉是明确实现错误

文件：`source/TempProject/LogSyncSettings.cs`

当前 `ShouldTestThreeViews()` 的实现是：

- `return autoTestScope == AutoTestScope.ThreeViews;`

而其他范围判断方法，例如 `ShouldTestTurrets()`、`ShouldTestRangedWeapons()`、`ShouldTestCombatPawns()`，都支持：

- `autoTestScope == AutoTestScope.All || autoTestScope == 对应范围`

这意味着只要选择 `All`，三视图就不会进入 `BeginThreeViewTestSession()`，因此被整轮测试直接漏掉。这个问题不是数据问题，也不是测试脚本问题，是设置层范围判断的逻辑 bug。

### 2. 口袋地图并发数当前是硬编码

文件：`source/AutoTestProject/AutoTestRunner.cs`

当前存在两组硬编码常量：

- `MaxConcurrentTurretTests = 3`
- `MaxConcurrentThreeViewTests = 1`

`TryStartNextPocketMapSession()` 中的调度方式是按不同 session 列表分别判断：

- 炮塔：`activeTurretSessions.Count < MaxConcurrentTurretTests`
- 远程武器：`activeRangedWeaponSessions.Count < MaxConcurrentTurretTests`
- 近战武器：`activeMeleeWeaponSessions.Count < MaxConcurrentTurretTests`
- CombatPawn：`activeCombatPawnSessions.Count < MaxConcurrentTurretTests`
- 三视图：`activeThreeViewSessions.Count < MaxConcurrentThreeViewTests`

这带来两个问题：

1. 口袋地图测试的并发上限不是统一概念，而是按测试类型各自计数。
2. 用户无法通过设置或脚本控制“当前最多同时存在多少张口袋地图”。

从最近一次 DMS 全量日志可以看到，当前运行时的确存在多 session 并发推进，例如：

- `CombatPawn heartbeat: 3 active sessions`
- 反复出现 `Pocket map shared cooldown refreshed: reason=create/destroy`

说明现在只有“共享 CD”，没有“统一并发总量上限”。

### 3. 自动测试生命周期里没有暂停/速度控制器

文件：`source/AutoTestProject/AutoTestBootstrap.cs`

当前 `AutoTestBootstrap.Tick()` 只负责：

- 等待地图稳定
- 自动 QuickStart
- 禁用日志自动弹窗
- 创建并驱动 `AutoTestRunner`

没有看到以下任何现成控制：

- 测试期间持续取消暂停
- 测试期间持续维持目标速度
- 测试期间屏蔽/压制某些会导致暂停的窗口或事件副作用

也就是说，现在自动测试只是“开始跑了”，但没有一个统一的“运行时护栏”去维持：

- 不中断
- 不降速
- 不被外部事件抢走节奏

### 4. 设置和脚本层尚未暴露这批运行时控制参数

涉及文件：

- `source/TempProject/LogSyncSettings.cs`
- `source/TempProject/LogSyncMod.cs`
- `规范化测试/run_test.py`

当前设置中只有：

- `autoTestScope`
- `autoTestBatchSize`
- `autoTestCaptureScreenshots`
- `autoTestMode`
- `autoTestTargetPackageId`

没有：

- 口袋地图统一并发上限
- 自动测试目标速度
- 自动测试期间是否强制取消暂停

这意味着即使只修 `Runner`，也无法从模组设置或测试脚本稳定控制新能力。

## 执行目标

本次改造的目标不是单纯“把 bug 修掉”，而是建立一个统一的自动测试运行时控制层，使后续新增测试类型也能直接复用。

具体目标如下：

1. `All` 范围真正覆盖 Content、Recipes、Hediffs、Turrets、RangedWeapons、MeleeWeapons、ThreeViews、CombatPawns。
2. 自动测试开始后，运行时持续维持非暂停状态，不被普通事件、袭击、重大通知打断。
3. 自动测试期间统一维持 2 倍速。
4. 所有口袋地图类测试共享同一个并发总量上限，默认值为 `5`，允许从设置和脚本传入。
5. 改造后每一类测试都能在日志中明确体现是否被调度、是否被限流、当前速度和暂停护栏是否生效。

## 改造方案

### 一、先修复“全量范围判定”

这是第一优先级，因为如果 `All` 本身不完整，后面的稳定性优化即使完成，也仍然是在跑一个不完整的测试集合。

计划改造：

1. 修正 `LogSyncSettings.ShouldTestThreeViews()`，让它和其他 `ShouldTestXxx()` 保持一致，支持 `AutoTestScope.All`。
2. 检查 `AutoTestRunner.Initialize()` 中各类 `BeginXxxTestSession()` 的调用顺序，确保三视图在 `All` 时一定会入队。
3. 补一层启动日志，在 `START` 之后输出本次启用的测试范围开关，避免以后再次出现“某类范围没被纳入”但日志看不出来。

预期结果：

- `scope=All` 时，三视图不再被静默跳过。
- 全量测试的 `planned/discovered` 能真实反映三视图目标数量。

### 二、引入“自动测试运行时控制器”

核心思路：不要把“取消暂停”和“强制速度”分散塞进各个 session，而是做成统一控制层，挂在自动测试主生命周期上。

建议落点：

- 入口仍然在 `AutoTestBootstrap.Tick()`
- 执行主体可放在新的运行时控制类，或者放进 `AutoTestRunner` 的统一前置阶段

推荐职责：

1. `EnsureUnpaused`
   - 每 tick 或固定 tick 间隔检查当前是否暂停。
   - 如果因普通事件、袭击、信件、通知或游戏速度变化导致暂停，则立即恢复为目标速度。
   - 日志只在状态变化时打印，避免刷屏。

2. `EnsureTargetSpeed`
   - 自动测试期间持续维持目标速度为 2 倍速。
   - 不仅在开始时设置一次，而是持续守护，避免被窗口或事件打回正常速度。

3. `OptionalEventPauseShield`
   - 第一阶段先做“恢复非暂停”，不急着深度 patch 全部事件系统。
   - 如果验证发现某些特殊窗口会持续抢暂停，再补针对性 patch。

这样做的原因：

- 自动测试关注的是持续推进，不是保留原版事件体验。
- 与其穷举所有可能暂停的事件源，不如先在运行时层做统一恢复。
- 这类逻辑属于框架能力，后续任何口袋地图、InfoCard、三视图测试都能复用。

### 三、把口袋地图并发总量抽成统一配置

当前的问题不是“值太小”，而是“概念错位”。

用户要求的是：

- 共存的口袋地图数量允许设置
- 默认值为 `5`

因此改造方向应该是“统一总量上限”，而不是把多个 `MaxConcurrent...` 分别改大。

计划改造：

1. 在 `LogSyncSettings` 新增类似 `autoTestPocketMapMaxConcurrent` 的设置项，默认 `5`。
2. 在 `LogSyncMod` 设置面板暴露这个值。
3. 在 `规范化测试/run_test.py` 增加对应参数，并写入 RimWorld 配置。
4. 在 `AutoTestRunner` 中统一计算当前活跃口袋地图 session 总数。
5. `TryStartNextPocketMapSession()` 改为先判断“当前总口袋地图数量是否已达到上限”，再决定是否拉起某类 session。

这里要明确两个设计原则：

1. 三视图如果继续使用口袋地图，也应该进入同一并发预算。
2. 共享 CD 和并发上限是两个不同维度，必须同时保留。

建议最终模型：

- `PocketMapSharedCooldownTicks` 继续负责创建/销毁节奏
- `autoTestPocketMapMaxConcurrent` 负责同时存在数量

这样可以避免：

- 同一时刻创建太多 pocket map
- 口袋地图反复快速开关导致截图或初始化不稳定

### 四、日志与可观测性补强

这次问题能较快定位，主要是因为已有 `heartbeat` 和 `Pocket map shared cooldown refreshed` 日志。后续应继续补强可观测性，避免再次出现“跑了但不知道为什么不全”。

建议新增的运行时日志：

1. 自动测试控制器状态
   - 自动恢复暂停是否触发
   - 当前目标速度是多少
   - 当前是否成功维持在目标速度

2. 统一口袋地图资源状态
   - 当前活跃 pocket map 总数
   - 各测试类型活跃数量分布
   - 因共享 CD 阻塞还是因并发上限阻塞

3. 三视图调度状态
   - 三视图目标是否已发现
   - 三视图目标是否进入 pending
   - 三视图 session 是否成功启动

这些日志要控制频率，建议只在：

- 状态变化时
- 每固定 tick 的 heartbeat 时
- 最终 summary 时

输出，不要按每 tick 刷屏。

## 验证方案

### 阶段 1：最小验证

目的：先证明控制层和范围修复生效。

测试内容：

1. 单独跑 `threeviews` 范围，确认三视图仍可正常执行。
2. 跑 `all` 范围的小批量测试，确认三视图不再缺席。
3. 手动在测试过程中制造游戏暂停，观察是否会自动恢复到 2 倍速。

验收标准：

- 日志中能看到三视图 session 进入 heartbeat。
- 日志中能看到速度/暂停控制器生效。
- 没有出现“测试停住但 runner 仍未结束”的情况。

### 阶段 2：并发验证

目的：验证统一并发上限确实按总口袋地图数量生效。

测试内容：

1. 将口袋地图并发设置为 `1`，跑一个会同时产生多类 pocket map 测试的目标模组。
2. 再设置为 `5`，对比日志里的活跃 session 总量。
3. 检查共享 CD 是否仍正常工作，没有被统一并发改造破坏。

验收标准：

- `1` 时，任意时刻只存在 1 张 pocket map。
- `5` 时，总活跃数不超过 5，而不是每类都各跑 5 个。
- 截图和地图开关稳定性不下降。

### 阶段 3：全量回归验证

目的：验证“真正全量测试”恢复成立。

测试内容：

1. 对目标模组跑 `all` 范围完整回归。
2. 对比本次 `planned/discovered` 与上次结果，确认三视图数量被纳入。
3. 检查是否仍有因暂停、速度切换、口袋地图拥塞导致的异常拖慢。

验收标准：

- 三视图不再缺失。
- 总测试项数量相比当前结果合理上升。
- 运行时无长时间无进展卡死。

## 实施顺序

建议严格按以下顺序执行，不要并行乱改：

1. 修 `ShouldTestThreeViews()` 和全量范围日志。
2. 加入自动测试运行时控制器，先只做“防暂停 + 强制 2 倍速”。
3. 抽取统一口袋地图并发上限配置，默认值 `5`。
4. 打通设置面板和 `run_test.py` 参数传递。
5. 做最小验证。
6. 做并发验证。
7. 做目标模组全量回归。

这样排的原因：

- 第 1 步先修覆盖率，不然后续所有验证都不可信。
- 第 2 步先稳住测试过程，不然第 3 步并发验证容易被事件暂停污染结论。
- 第 4 步最后补入口层，避免反复改 UI 和脚本参数。

## 风险与注意点

### 1. 不要把“防暂停”误做成“禁用所有事件”

目标是保证自动测试持续推进，不是永久改写游戏玩法。第一阶段应优先采用“测试期间自动恢复运行状态”，而不是大面积 patch Incident 系统。

### 2. 并发上限必须是“总量”而不是“每类”

如果只是把 `MaxConcurrentTurretTests` 从 `3` 改成 `5`，会出现多类 session 同时各跑 5 个的问题，实际口袋地图总量反而会失控。

### 3. 三视图是否占用口袋地图预算要统一定义

不能出现：

- 炮塔/武器/CombatPawn 受总量限制
- 三视图另走一套独立上限

否则“全量测试时的地图资源”还是不可预测。

### 4. 日志需要能证明控制器在工作

后续如果再次出现“测试卡住”或“某类范围没跑”，必须能直接从日志判断是：

- 范围未入队
- 并发受限
- 共享 CD 阻塞
- 被外部事件暂停
- 速度守护失效

## 结论

这次问题的优先级排序应为：

1. 修复 `All` 不包含三视图
2. 建立自动测试运行时控制器，保证不暂停且维持 2 倍速
3. 将口袋地图并发改为统一可配置，默认 5
4. 打通设置界面与 `run_test.py`
5. 以小批量验证后再进行真正全量回归

在这套顺序下，后续得到的“全量测试结果”才具备可信度。否则即使单个测试项逻辑正确，整轮回归仍然会因为覆盖率缺失或运行时失控而不可靠。
