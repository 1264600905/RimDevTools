## 4. 第一批：旧项目模式与三包发布基础

### 4.1 配置字段

在 `ProjectConfig` 中新增布尔字段，并同步两种模板的配置源文件及配置说明：

```jsonc
// 已有项目按现有工程与同步配置使用工具，放宽模板专属限制。
"existing_project_mode": true
```

- 新模板显式写入 `false`；旧配置缺失字段时按 `false` 读取。
- 开关为 `true` 时，不要求模板来源清单，也不自动改变 `csproj_paths`、`sync_items`、`game_version`、日志关键词或模组身份。
- 字段接受 JSON 布尔值；错误类型按配置错误报告，不把字符串 `"true"` 等隐式转换为有效值。
- 读取配置、执行部署或 doctor 不为补全字段而自动重写配置文件。
- 旧项目手动设置该字段后即可沿用已有命令，不增加其他接入前置条件。

### 4.2 分离模板专属检查与通用检查

当前 `ProjectTemplatePreflight` 混合了模板占位符、日志关键词和 About 文件检查，并被 deploy、doctor、test settings 与 test run 复用。实施时逐项区分检查的用途，不能通过跳过整个预检丢失必要错误。

| 检查类别 | 普通模板模式 | 旧项目模式 |
| --- | --- | --- |
| 名称、packageId 是否等于模板默认值 | 保持现有门禁 | 不作为模板占位符拦截理由 |
| 工程路径、程序集名称中出现 `MyCustomMod` 等模板标识 | 保持现有门禁 | 按实际路径和构建结果处理，不仅凭模板标识拦截 |
| 固定模板版本目录下的默认 DLL 检查 | 保持现有门禁 | 不要求旧项目采用该模板目录及 DLL 命名 |
| 日志关键词是否等于模板值、是否填写专属关键词 | 保持模板模式现有规则 | 不作为普通部署的模板门禁；测试功能按其真实运行需要检查 |
| 配置可解析、部署名称非空、游戏目标受支持 | 保留 | 保留 |
| About 缺失、不可读等部署必需信息问题 | 保留 | 保留，不用模式开关掩盖 |
| 工程缺失、构建失败、同步源和目标不合法 | 保留 | 保留 |
| 越界路径、重解析点、位于 Mods/Workshop 内等位置保护 | 保留 | 保留 |
| 测试宿主、依赖、ModsConfig、日志运行条件 | 按对应命令检查 | 按对应命令检查，模式字段不代表测试已经可用 |

实施要求：

1. 检查所有共享预检调用点，保证 deploy、doctor 与测试入口对模式的理解一致。
2. doctor 能说明当前项目模式，不再把旧项目的模板差异报告为必须修复的部署问题。
3. 对只影响测试的条件，保留在测试入口或相应诊断项中；不反向增加普通部署限制。
4. 使用现有构建、同步和部署事务。普通模式及缺省字段的行为保持兼容。
5. 不新增 DLL 源目标映射、独立内容根、任意构建脚本支持、游戏 API 迁移或工程文件自动改写。当前路径配置不能表达的布局，仍按实际原因说明。

### 4.3 三种发布包

保留两种模板包，新增简化工具包，建议命名约定固定为：

```text
RimDevTools-<工具版本>-Template-RimWorld-1.6.zip
RimDevTools-<工具版本>-Template-RimWorld-1.7.zip
RimDevTools-<工具版本>-Tools.zip
```

版本从实际构建和发行元数据取得，统一三段与四段版本的比较规则，不在代码中硬编码当前发行号。

简化包内容：

- `.tools/RimDevTools.exe`。
- 正式发行的 `.tools/Data`、工具组件清单、必要的 1.6/1.7 配套载荷。
- `.tools/Ilspy`、相应许可证和发行范围内的 `.tools/modlist` 预设。
- `.agents/skills/rimdevtools/**` 与 `.claude/skills/rimdevtools/**`。
- 根目录 `mod_config.jsonc` 配置参考及机器可读的工具发行清单。

配置参考用于人工填写。已有配置由用户维护；更新器只执行明确的配置迁移规则，不能把包内参考配置覆盖到项目。参考配置清楚标记人工填写项，不携带开发者本机路径；旧项目模式示例为 `true`，实际游戏版本由项目明确设置。

简化包不包含模组示例源码、About、Defs、Languages、模板 DLL、项目 README、模板身份文件、`.gitignore`、其他 skill、MCP/编辑器设置、项目运行数据或测试证据。必要许可证保留在工具发行范围内。模板包保留各自原有的新建项目内容。

三包必须使用同一发行的 EXE、两份核心 skill 及必要工具组件。共用载荷只构建或准备一次，组装时复用；同一路径上的共用工具文件哈希一致。两种游戏的组件都要实际校验，不能仅在清单中声明兼容。

### 4.4 发行清单与初始基线

在现有发布脚本内建立正式的工具文件清单，供第二批更新使用。它与模板布局清单分别表达各自用途。

清单至少包含：

- 清单结构版本、工具版本、平台/架构、Runtime 要求及支持的游戏版本。
- 受管理文件的相对路径、大小、SHA-256、内容角色和更新策略。
- 核心 skill 的完整文件集、组件版本及必要的关联约束。
- 当前可接受的配置结构版本和明确的迁移规则。
- 配置参考与实际替换文件的区别；模板专用元数据不归简化包更新。

清单中的文件路径按白名单生成，清单不递归记录自身哈希。包内文件完整性与整个 ZIP 的下载完整性分别验证。

新发行包带有可用于验证初始工具内容的只读发行清单，不打包某个用户的 `.tools/ProjectData`。首次建立运行态基线时，先核对磁盘内容与已知发行清单。历史安装缺少基线且无法核实时，第二批必须报告无法确认归属或本地修改，不能默认允许覆盖。

## 5. 第二批：自动更新

### 5.1 CLI 与结果约定

```text
RimDevTools.exe update --check
RimDevTools.exe update --dry-run
RimDevTools.exe update
RimDevTools.exe update status
```

| 入口 | 行为 |
| --- | --- |
| 普通业务命令启动 | 在预算内检查或读取缓存，有新版时提示；不安装 |
| `update --check` | 显式查询，区分存在新版、已是最新和无法确认 |
| `update --dry-run` | 固定目标发行，取得验证计划所需内容，列出文件变化、配置迁移和冲突；不提交工具或配置替换 |
| `update` | 校验并准备更新，交接给独立助手；未完成替换时只报告 `scheduled` |
| `update status` | 本地只读查询最近一次事务；不联网、不触发安装 |

`--dry-run` 可以使用工具管理的下载缓存或暂存，但不能修改当前安装内容、配置、安装基线或提交状态。参数互斥和未知参数按现有 CLI 约定处理。

stdout 继续只包含一个最终 JSON；提示写入 stderr。`scheduled` 仅表示交接已完成，不表示安装成功。返回结果至少能识别当前/目标版本、事务标识、真实状态、冲突或失败原因及需要用户操作的原始路径。

### 5.2 来源、缓存与版本判定

1. 固定官方仓库来源，通过正式 Release 元数据选择对应 Tools 附件；默认排除预发布和草稿。
2. 用数值版本比较并规范三段/四段表示，拒绝隐式降级；同版本通常返回无需更新。
3. 普通启动检查采用 24 小时缓存，联网总预算最多 2 秒。网络失败、离线和限流采用退避，不影响业务命令退出码。
4. 显式检查如实报告无法确认；不能把超时或查询失败当成已经最新。
5. 实际更新开始时重新确定目标，并固定 Release、附件及校验信息，整个事务不再追随变化中的 latest。
6. 核对平台、Runtime、项目游戏版本和配置兼容范围。检查更新不依赖 Steam、游戏已安装或游戏环境健康；安装也不运行完整游戏 doctor。
7. 不强制公开仓库用户配置 GitHub 账号或 token，不在发行包中保存发布者凭据。

### 5.3 更新范围和冲突规则

| 内容 | 更新处理 |
| --- | --- |
| EXE、必要 Data、ILSpy、许可证与发行预设 | 依据工具清单及基线更新；仅清理由清单确认已移除的旧受管理文件 |
| 两套 `rimdevtools` skill | 更新完整文件集；本地修改或无法确认基线时，阻止整次提交并列出冲突 |
| `mod_config.jsonc` | 保留式迁移；不作为普通替换文件 |
| 模板身份元数据 | 保留原模板游戏目标和布局含义，不写成当前工具版本所对应的新模板 |
| 模组源码、资源、README、其他 skill、AI/MCP 设置、`.gitignore`、工坊身份与项目历史 | 不纳入更新替换或清理 |

更新已有工具文件前核对预期旧哈希；需要删除的旧受管理文件也必须核对。用户增加的未受管理文件原样保留；若占用新版本需要写入的路径，则报告冲突。不得通过清空整个目录实现更新。

首次缺少运行态基线时，可用当前版本的已知正式发行清单验证并建立基线；未知来源或内容无法核对时停止提交，说明冲突及处理方式。不能把“没有基线”当作“没有修改”。

更新游戏目录内的 LogSyncMod 仍使用已有 `mods install-tools` 等流程。更新项目私有载荷后只说明两处状态，不声称游戏内组件已同步。

### 5.4 JSONC 保留式迁移

- 首版接受 `config_version=2` 的明确迁移路径；其他结构版本给出不支持的错误，不猜测转换。
- 本次新增模式字段后仍使用版本 2；更新迁移只为缺失字段补充默认 `false`，已有 `true` 或 `false` 都保留。
- 保留 `game_version`、模组身份、工程和同步列表、各类路径、关键词、依赖、超时、保留策略及其他用户值。
- 对 `false`、`0`、空数组和显式 `null` 按字段语义处理；错误值报告错误，不能因为值为空就无条件覆盖。
- 保留未知字段、注释、换行风格和可保留的格式。采用局部文本编辑或等效保留机制，不通过固定类型读取后整体序列化回写。
- 新增字段、改名或语义变更由发行规则明确描述，嵌套字段和数组分别处理。
- 候选配置先解析验证，提交前再次核对原始文件哈希；解析失败、重复键导致歧义或并发修改时不覆盖原文件。

### 5.5 下载、助手与事务提交

按以下顺序实现，并在写入前完成能够提前执行的验证：

1. 从正在运行的正式安装定位 EXE、所属项目及配置，核对安装关系；不因当前工作目录改变而更新另一个项目。
2. 下载 Tools 附件到工具自身管理的位置，校验大小和 SHA-256。API 未给出 digest 时使用发行方提供的校验清单；缺少可靠校验信息则停止。
3. 按白名单解包和核对文件，拒绝路径穿越、大小写碰撞、越界路径及不允许的链接/重解析点。
4. 生成完整变更计划，处理基线、本地冲突、配置候选和组件兼容；提交前不替换当前工具文件。
5. 取得安装级排他门禁，核对同一安装下正在执行的其他命令。繁忙时明确返回或有界等待，不终止用户进程。
6. 写入可恢复的事务与交接状态，准备独立助手；助手确认可继续后，主进程返回 `scheduled` 并退出。
7. 助手等待原进程真正退出，重新核对门禁和目标文件，然后按日志记录的顺序替换 EXE、skill、配置和必要组件。
8. 完成无游戏验证：新 EXE 可运行、版本正确、配置可解析、受管理文件与组件清单一致。
9. 验证通过后提交新基线并标记 `succeeded`；失败时恢复整组旧文件和旧基线，记录 `rolledBack` 或 `recoveryRequired`。

采用安装级门禁，不能仅复用按游戏配置目录划分的 `EnvironmentLock`。门禁覆盖所有会使用该安装的正常业务命令，并用持久交接状态封闭父进程退出到助手接管的空档。新命令遇到更新中或需恢复的安装时，给出明确状态，不使用混合版本继续业务。

主进程不能等待助手完成替换，同时让助手等待主进程退出。助手启动、握手或交接失败时不能返回已安排成功。助手以隐藏窗口启动，不自动重跑原业务命令。

源码运行和正式解压安装应能区分；禁止更新器覆盖开发仓库、模板源文件或本地构建输出。识别依据来自安装布局与受管理元数据，不能只凭目录名或是否存在 `.git`。

### 5.6 状态与中断恢复

事务至少区分以下状态，具体 JSON 字段保持稳定：

| 状态 | 含义 |
| --- | --- |
| `none` | 尚无安装事务 |
| `scheduled` | 助手已接收，等待原进程退出或开始提交 |
| `applying` | 正在替换受管理文件 |
| `succeeded` | 替换及安装后验证完成 |
| `failed` | 提交前失败，当前安装未发生部分替换 |
| `rolledBack` | 提交或验证失败，已完整恢复旧安装 |
| `recoveryRequired` | 恢复未完成，普通业务命令被阻止 |

根据事务日志、进程身份及实际文件状态识别中断，不能只依赖内存锁或某个 PID。状态查询只读取；恢复由内部助手或明确的恢复入口执行，恢复路径和使用方法随状态返回。

主 EXE 不能运行时，仍须能通过工具保留的独立助手完成恢复。未恢复事务的必要助手与回滚数据不能被缓存清理误删。清理只涉及工具自身拥有且已经完成的运行数据。

更新缓存、状态、暂存和回滚文件使用工具管理的 `.tools/ProjectData` 运行数据位置；具体文件布局由实现统一定义。这些是更新功能数据，不是为测试另建的证据归档。本次编写计划不创建这些目录。
