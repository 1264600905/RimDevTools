# RimWorld 1.7 功能回迁到 1.6（master）实施计划

> 执行目标：从 `master`（1.6）回迁功能，并用同一个 Mod 包支持 1.6 和 1.7。按四批实施；每批部署、启动本机游戏检查红字，通过后提交。不开启自动测试。

## 2. 可行性与证据

### 结论

**已验证：**当前 1.7 分支新增的游戏内功能可以作为一个整体回迁到 `master`。按 `master` 的 .NET Framework 4.7.2 项目和本机 1.6 游戏程序集做的临时编译探针，没有发现缺失的 RimWorld、Unity 或 Harmony API 符号；探针只报出 3 个可定位的 C#/.NET 兼容错误。

**已验证：**同包双版本可使用版本化 `LoadFolders.xml` 分流 Def 与程序集；本机 1.7 `LogSyncMod.dll` 与已记录的 1.2.6 文件哈希一致（`616FC2F4D1470827C0AF897BD3BA6D4EEC0F3954D45E6AB62DBD3BC7E640FBC6`），且已部署于当前模组目录。

**推断：**不需要因为公开 API 差异而删掉功能，也不需要重编 1.7 DLL。主要工作是按四批把 1.6 源码与 Def 补齐，恢复 1.6 构建配置，处理两类编译兼容点；每次部署保留 1.7 DLL 与其 Def。编译通过不代表复杂补丁在游戏运行时一定等价。

### 已验证事实

1. 回迁目标是 `master` 当前基线 `835916c`：根目录 `LoadFolders.xml` 选择 `v1.6`，`source/LogSyncMod/LogSyncMod.csproj` 目标为 .NET Framework 4.7.2 并输出到 `1.6/Assemblies`。当前分支 `a83547d` 则把主模组项目改成 `net10.0`，并引用 1.7 的 `UnityStubs`、`Waylith` 和游戏程序集。此项目设置不能原样带回 1.6。
2. 当前分支相对 `master` 新增的主要游戏功能位于 `source/LogSyncMod/DebugTools/`：物资配置与方案、物资放置、需求锁定、技能/工作状态、灵能与机控开关、快速治愈、工作台材料生成。`source/AutoTestRunner/` 的源码和项目没有随这些功能改动。
3. 主模组差异还包括 `LogSyncSettings` 中的物资方案持久化字段、Debug Hediff Def、翻译、About 与部署配置。`1.7/Defs/Internal/TestDefs.xml` 与 `1.6/Defs/Internal/TestDefs.xml` 的哈希一致；回迁无需复制或改写这份测试 Def。
4. 我用当前源码、1.6 的 `Assembly-CSharp.dll`、Unity 模块、Harmony 和 `net472` 引用做了临时 Release 编译探针。完整错误为：
   - `DebugSupplyPreset.cs:62`：C# 7.3 无法推断 `string` 与 `TaggedString` 条件表达式的共同类型（CS8957）。
   - `DebugWorkbenchIngredients.cs:128`：.NET Framework 4.7.2 没有 `float.IsFinite` 和 `double.IsFinite`（CS0117）。
   - 没有其他缺失的游戏程序集成员错误。该探针没有改动仓库源码，也没有运行游戏或测试。
5. 对照 1.6/1.7 游戏源码，几个高风险调用的签名一致：`Need.CurLevel`、`Need.IsFrozen`、`Need.NeedInterval`、`Pawn_WorkSettings.GetPriority`、`Pawn_TimetableTracker.CurrentAssignment/GetAssignment`、`Hediff_Psylink.ChangeLevel(int, bool)`、`IngredientCount.CountRequiredOfFor`、`Pawn_MechanitorTracker.Notify_BandwidthChanged`。1.6 源码还确认 `Need.curLevelInt` 为受保护字段，符合当前 Harmony 补丁的字段注入方式。
6. Ludeon 对 1.7 的公告说明它更换为 Waylith 引擎，并说大多数 1.6 模组可直接在 1.7 使用；这个保证是从 1.6 到 1.7 的方向，不能单独证明反向兼容。[Ludeon：Announcing the Waylith Engine and Update 1.7](https://ludeon.com/blog/2026/10/announcing-the-waylith-engine-and-update-1-7/) 社区的 1.7 更新指南记录了 `net10.0`、Waylith/Unity 引用和 Harmony 3 的 1.7 项目要求；这些要求与 `master` 的 1.6 项目设置不同。[RimWorld 1.7 Mod Updates](https://rimworldwiki.com/wiki/Modding_Tutorials/RimWorld_1.7_Mod_Updates)

### 尚未验证

- **未解决：**本机安装为 RimWorld 1.6.4871，没有 1.7 游戏进程可用于本机启动验收。1.7 侧以现存 DLL 哈希和版本化资源保持不变为准；运行时快速检查以本机 1.6 为准。
- **未解决：**动态补丁能否覆盖用户所有目标模组的 Need、工作台和 Job 流程，仍要按实际模组列表验收。

## 3. 可落地修改计划

### 实施范围

从 `master` 建立单独的双版本分支（`codex/logsync-dual-versions`）。根目录共享 About/语言文件；`LoadFolders.xml` 按版本分别加载 `1.6/` 与 `1.7/`。1.6 从当前源码用 `net472` 构建；1.7 保留现有 DLL 和最终版 1.7 Def，不引入 1.7 分支的 RimDevTools/模板改造或 `net10.0` 构建。

### 四批与 1.7 上游提交映射

| 批次 | 回迁范围 | 对应 1.7 提交 | 快速验证重点 |
| --- | --- | --- | --- |
| 1 | 调试物资窗口、放置、命名方案与基础调试入口；建立双版本包骨架 | `44f872d`、`48a8769` | 1.6 加载无红字；物资窗口打开、保存方案、选点放置 |
| 2 | 工作/暴力解禁、全工作、技能与工作速度、全天作息、移速/携带；全需求锁 | `4a52f40`、`ed19aae`（需求部分）、`a83547d` | 1.6 加载无红字；框选开关、技能/工作页与需求变化 |
| 3 | Royalty 灵能与 Biotech 机控/带宽开关 | `908f78f` | 1.6 加载无红字；两 DLC 当前均启用，检查工具入口及加/撤状态 |
| 4 | 快速治愈、工作台原料生成与最终文案/资源同步 | `ed19aae`（治愈与工作台部分） | 1.6 加载无红字；治愈入口、工作台按钮和一轮原料生成 |

每批完成修改后先构建 1.6、部署双版本包、启动本机 1.6 检查主菜单/游戏内是否有红字；通过后再提交。提交说明必须写出该批对应的 1.7 commit SHA。不开自动测试。

### 有序步骤

1. **批次1** — 从 1.7 上游提交移植物资窗口、方案和放置功能；合并 `LogSyncSettings` 序列化字段。为 `string`/`TaggedString` 条件表达式增加显式转换，以兼容 C# 7.3。
2. **批次2** — 移植工作/技能/需求完整状态与移速、携带加成；在 `float.IsFinite` 与 `double.IsFinite` 处改用 `IsNaN/IsInfinity` 组合，兼容 .NET Framework 4.7.2。
3. **批次3** — 移植灵能/机控状态和 DLC 条件 Def，保留原等级/植入物撤销与读档序列化。
4. **批次4** — 移植快速治愈、工作台原料生成和对应的 `DebugSupplySpawner` 扩展。
5. **维护双版本资源** — `LoadFolders.xml` 同时声明 `v1.6` 和 `v1.7`，两边各加载根目录与对应版本目录；`About/About.xml` 支持 1.6、1.7。保留 `master` 的 1.6 `LogSyncMod.csproj` 与 AutoTestRunner 构建；`mod_config.jsonc` 以本机 1.6 为构建目标、同步两套 Assembly/Defs。1.7 DLL 哈希必须保持上文记录值。
6. **逐批构建、部署与快速验证** — 每批运行 `dotnet build source/LogSyncMod/LogSyncMod.csproj --configuration Release` 和 `dotnet build source/AutoTestRunner/AutoTestRunner.csproj --configuration Release`；使用 RimDevTools 部署整包后启动本机 RimWorld 1.6.4871，检查是否出现红字并检查本批入口/行为。通过后提交，提交说明包含上游 1.7 SHA。不开自动测试。
7. **最终 1.6 行为核对** — 在 1.6.4871 上用复制存档和当前启用模组清单做以下聚焦检查：
   - 物资弹窗：搜索、分类/模组过滤、数量、命名方案保存/读档、地图边缘和空间不足时的生成统计。
   - 需求锁：原版 Need、至少一种模组 Need、持续经过多个 NeedInterval、保存/读档、再次框选解除；无标记 Pawn 不受影响。
   - 技能与工作状态：技能显示、工作优先级、禁用工作/暴力、24 小时工作表；混合状态目标、重复框选、读档后撤销。
   - 灵能/机控：Royalty 与 Biotech 分别单独启用、同时启用、均未启用；已有低级灵能、已有机控中枢、重复框选和读档恢复。
   - 快速治愈：伤口/旧伤/缺失部位、常见疾病与药物效果；确认义肢、植入物、妊娠、基因性依赖及测试标记不会误删。
   - 工作台原料：普通配方、品质/材质筛选、固定原料、尸体原料、模组工作台、首项账单暂停或已完成、原料生成位置不足。
8. **最终包核对** — 确认 `1.6/Assemblies/LogSyncMod.dll` 是本轮构建产物，`1.7/Assemblies/LogSyncMod.dll` 哈希未变化；两版对应 Def 存在，部署目标包同时含两套目录。

### 不承诺完全覆盖的边界

- 全需求锁仅覆盖使用游戏 `Need` 类型及其继承链的需求实现；完全独立的资源条或绕过 `Need` 的模组系统不在通用补丁承诺内。
- 全工作与技能效果依赖 `SkillRecord`、`Pawn_WorkSettings` 和 `WorkTypeDef`；自建工作/技能系统需单独接入。
- 快速治愈只清理按定义、组件或事件关系能确认的疾病/药物 Hediff。未声明这些关系的自定义状态应保留，避免误删。
- 工作台材料按钮针对 `IBillGiver` 与原版 `ITab_Bills` 流程；特殊自定义工作流可以拒绝生成，而不猜测其原料语义。
- 灵能/机控功能按已启用 DLC 分别生效；没有对应 DLC 时保留其余工具功能。

## 4. 风险与回滚

| 风险 | 等级 | 处理方式 |
| --- | --- | --- |
| 1.6 Harmony 对动态目标补丁的运行顺序或注入行为与 1.7 实际不同 | 高 | 先用纯净 1.6 和常见模组各验一次；Need、Building.GetGizmos 和技能/作息读取分别检查日志与实际结果。 |
| 模组 Need/工作台重写方法，或自定义配方 Worker 不走原版路径 | 高 | 以原版路径为必需验收；模组路径作为兼容验收，无法安全识别时明确跳过并给出消息。 |
| 保存后 Pawn 身上仍有新增测试 Hediff | 中 | 测试只用复制存档。若回退程序集/Defs，先清理 `LogSync_DebugNeedsLock`、`LogSync_DebugSkilledWorker10x`、`LogSync_DebugNeuralTest` 状态；不要在含这些状态的存档上直接移除对应 Def 或 Hediff 类。 |
| 1.7 构建产物被后续本机 1.6 构建覆盖或遗漏 | 中 | 每批部署前后核对 1.7 DLL SHA-256；1.6 项目固定输出 `1.6/Assemblies`，不写入 `1.7/Assemblies`。 |

回滚时保留本次回迁为单独提交/分支；测试期间只用复制存档。若已在真实存档添加测试 Hediff，先移除状态再回退，或保留兼容 Def/类直到相关存档清理完成。

## 5. 实施难度

**难度：★★★☆☆（3/5）**

理由：1.6 的关键游戏 API 已能绑定当前新增代码；本机已有完整 1.7 DLL 与资源，双版本分流由 `LoadFolders.xml` 和 `1.6/`、`1.7/` 目录完成，无需重做 1.7 运行时。工作量主要是四批回填、两类编译兼容修正，以及每批在 1.6 上部署启动检查。风险集中在 Harmony 覆盖面和复杂配方的运行时行为。
