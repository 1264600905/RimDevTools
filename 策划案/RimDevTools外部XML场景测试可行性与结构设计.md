# RimDevTools 外部 XML 场景测试：可行性与结构设计

记录日期：2026-11-06。

状态：第一、二批已实现并完成真实测试。基础语法见[第一批使用说明](RimDevTools外部场景XML第一批使用说明.md)，新增能力与验收见[第二批使用说明](RimDevTools外部场景XML第二批使用说明.md)和[第二批完成清单](RimDevTools外部XML场景测试_第二批完成清单.md)。本文保留完整需求与后续设计，第三、四批尚未实现，示意标签不代表全部已交付。

分批实施与验收以[四批实施计划](RimDevTools外部XML场景测试四批实施计划.md)为准：每批独立实现、测试和提交，并携带本批完成清单。本文保留需求细节及设计依据。

原生复用范围已确定，详见四批实施计划第 2.3 节：仅直接接入角色生成、地图生成和游戏行为接口；外部配置、精确覆盖及测试控制由工具实现。Prefab、原生房间布局、点数组队、Scenario/Quest 和完整原生 XML 加载器不新增独立接入。

## 1. 目标与定位

增加由外部 XML 描述的共享场景能力，支持全部既有非 UI 测试的高度自定义。回归场景用于补充现有代码生成的 `auto` 自动测试，解决通用测试无法正确准备前置条件、无法准确触发或判断特殊机制的情况；独立的群战测试使用同一套场景定义进行战斗数值评测。

用户提出的主要需求：

- XML 位于用户指定的文件或文件夹，不放进模组本体。
- 明确描述测试目标、场景、执行逻辑及成功条件。
- 除 UI 检查之外，既有全部战斗、技能、视图和实际功能测试均须支持自定义，不能只实现群战或少量技能。
- 每条自行编写的 XML 测试规则必填唯一稳定的 testDefName，与被测游戏 DefName 和执行实例 caseId 分开。
- 目标可以是 Pawn、建筑、普通 Thing 或尸体。
- 能配置 Pawn 的服装、武器、特性、工作技能等级、健康效果和特殊技能。
- 能配置敌人和友军的种类、数量、装备、健康效果等。
- 支持截图、战斗、技能及自定义效果验证。
- 可以通过目标新增指定 Hediff、生成指定 Thing、自身新增效果等条件判断成功。
- 能继承某个 PawnKind 的原生生成结果，再局部替换装备等配置。
- 可以声明补充或替代哪些 DefName 的自动测试，允许一份配置关联多个目标。
- 可以在测试过程中执行固定格式的 DebugAction，选择方式仅允许单体和矩形框选。
- 新增独立的“群战测试”，支持最多三方的群体对抗，统计每方和每个单位的输出、DPS、承伤、存活及胜负结果。
- 群战测试用于评测数值，必须明确选择群战类型并指名具体测试，不随常规 Bug 回归测试自动执行。
- 群战期间在屏幕左右显示双方的输出与承伤 Top10 条形榜、单位名称及图标；人类角色使用实际渲染的角色图，阵容最多显示当前数量最多的五种单位及 `X存活数量`，下面显示实时更新的平均 DPS 和承伤。
- 群战新建普通主地图开展评测，完成后丢弃该地图，不使用口袋地图。
- 测试地图支持预设环境和自定义生成器，包括具有自然日照的场景。
- 按指定整套配装生成 Pawn 三视图，作为面向玩家的装备组合展示。
- 新增两个游戏内 DebugAction：自动暂存角色数据、打开普通自动测试弹窗。左右 TAB 批量选目标和统一选战斗/UI/三视图类别；首次无记录时类别全选，开始即关窗，重开恢复上次测试选择。角色数据保存到 ProjectData 并跨重启读取。
- 游戏内“同类”指本次游戏启动内全部手动执行的测试：首次由工具创建正式产物路径，后续本次启动全部追加，重启游戏后新建汇总；与 RimDevTools 自动测试分开。

建议将共享功能命名为“外部场景测试”。普通 `auto` 继续承担广泛扫描，外部回归场景负责针对已知机制进行精确验证；群战属于独立的数值评测用途。

UI 排除范围指信息卡、窗口、菜单、按钮和 Gizmo 界面交互，不删除原有 UI 测试。地图/角色/物品截图属于 View，仍须自定义；配方生产、健康变化等真实功能即使位于现有 UI 用例中，也要拆出功能部分支持自定义。逐类参数、动作、判据、交付批次与验收要求以四批实施计划第 2.4、8.3 节为准。

这里的外部 XML 提供可共享的场景定义：角色、配装、健康状态、技能、敌友编组、地图预设和准备动作等，均可供技能测试、其他口袋地图测试及新增群战测试使用。提前设计这些定义，是为了让各类测试复用同一套场景准备能力。

“群战测试”是新增的独立数值评测类型，主要用于一群单位与另一群单位交战，也可以加入第三方。DPS、累计输出、承伤分布、各方剩余单位及胜负统计属于群战测试的新增内容。群战必须显式指定测试类型及具体测试名称，使用新建且完成后丢弃的普通主地图；其数值结果与此前用于发现 Bug 的测试分开处理。技能测试和其他口袋地图测试可以使用同样的场景定义，按各自的目标执行与验证；使用共享定义不会自动启用群战统计，也不要求先实现群战测试。

## 2. 可行性结论与实现基础

可行。现有系统已有执行记录、目标引用、条件等待、断言、截图、结果报告和口袋地图清理恢复，可以作为共享执行能力复用。群战需要新增普通主地图生命周期、数值统计和屏幕实时显示，地图释放采用普通主地图的处理方式。

| 能力 | 当前基础与新增工作 |
| --- | --- |
| 执行与异常记录 | 复用 `AutoTestOperationRunner`、操作日志及证据上下文 |
| 等待与超时 | 复用 `AutoTestWaitHandle`，区分实际时间和游戏 tick |
| 效果断言 | 复用断言与 Pawn、Thing、Ability 等探针，补充新的标准谓词 |
| 场景环境 | 技能及其他口袋地图测试复用现有地图服务；群战新增普通主地图后端，共享场景装配和资源归属管理 |
| 清理恢复 | 复用异常隔离和实时恢复设计；分别处理口袋地图清理与群战普通主地图丢弃 |
| 外部输入 | 新增 XML 结构、严格校验、路径加载和计划编译 |
| Pawn 配置 | 新增生成约束、局部覆盖和配置后验证；工作技能、特性等需补齐配置能力 |
| 补充与替代 | 新增覆盖映射及完整性验证，避免仅凭声明就计为成功 |
| DebugAction | 新增固定注册和无交互适配，不能直接依赖调试菜单流程 |
| 群战测试（新增数值评测类型） | 复用共享场景定义，新增指名运行、普通主地图、群体对抗调度、伤害账本、分布统计及屏幕实时榜单；当前战斗探针不能直接作为完整 DPS 账本 |
| 地图预设 | 共享预设与环境描述，按口袋地图和普通主地图分别检查生成器适配性；群战固定使用普通主地图 |
| 整套配装展示 | 复用三视图与截图基础，增加完整配装保留、同一角色多方向一致性和展示输出 |
| 游戏内普通测试弹窗 | 复用菜单注册、刷物品式筛选/多选和内置执行能力，新增左右 TAB、批量目标与统一类别、角色数据和本次启动汇总 |

共享场景能力的主要工程量在场景编排、正确准备 Pawn 上下文、特殊机制适配及覆盖验证。群战测试另有普通主地图生命周期、对抗调度、伤害账本、统计与屏幕显示工程量，应独立评估和交付。读取 XML 本身只是输入层。

历史上的 [XML 驱动自动测试移除计划](RimDevTools_XML驱动自动测试移除实施计划.md)针对的是模组内 `LogSyncAutoTestSpecDef` 流程。本方案不恢复向模组 Defs 写入测试定义的方式，而是使用独立解析器读取外部场景，引用已经加载的游戏 Def。

## 3. 外部文件入口与加载规则

回归场景建议扩展现有 `auto` 入口；群战建议提供独立的显式入口，并要求具体测试名称。以下命令及参数仅为设计示意：

```powershell
# 与普通技能自动测试合并，按 XML 中的覆盖规则补充或替代
RimDevTools.exe test run --mode auto --scope skillpocketmaps `
  --scenario-path "D:\ModTests\Axolotl"

# 只运行指定外部场景，便于调试配置
RimDevTools.exe test run --mode auto `
  --scenario-path "D:\ModTests\Axolotl\movement.autotest.xml" --scenario-only

# 显式选择群战数值评测，并指名一个具体测试
RimDevTools.exe test run --mode groupcombat `
  --scenario-path "D:\ModTests\Combat\wolves-vs-bears.autotest.xml" `
  --test-name "Example_GroupCombat_WolvesVsBears"
```

建议规则：

1. 指定文件时读取该文件；指定文件夹时只枚举 `*.autotest.xml`。是否递归需要显式约定，首版建议默认不递归。
2. 不传入外部场景路径时，现有自动测试行为不变。
3. 不将 XML 部署到 Mods，不上传工坊，不加入游戏 Def 数据库，也不通过全量 Def 热重载应用测试配置。
4. 开始运行时固定文件清单、内容哈希和解析后的计划，避免测试期间编辑文件导致前后混用。
5. CLI 在启动前检查 XML 语法、结构和引用关系；实际 Def、身体部位、依赖及动作绑定在游戏加载完成后验证。
6. 未知字段、错误类型、重复 ID、模板循环、无法解析的目标，以及缺失/重复 testDefName，给出文件、行号和字段路径，不能静默忽略；测试定义名按全部加载文件和 Suite 全局检查。
7. 禁用 DTD 和外部实体解析；XML 不包含任意 C#、自由表达式或反射方法调用。
8. 所有结果、截图、日志和测试存档继续由 RimDevTools 管理，沿用工具生成的原始产物路径。XML 不另行指定证据归档目录。

游戏内手动测试通过第 17 节的两个 DebugAction 发起，无需玩家编写 XML 或运行 CLI。首次手动执行分配正式路径，本次游戏进程启动内所有手动测试均追加到同一会话；回主菜单或切存档不拆分，退出重启后另建手动汇总，不复用自动测试会话。

第二项只运行无需作者手写测试 XML 的内置普通 UI/非 UI 测试，不加载外部测试规则或群战。目标与内置测试类别在左右 TAB 统一选择；外部 XML 自定义能力继续由其独立入口交付，具体范围与验收见四批实施计划第 2.6、8.4 节。

暂存角色 XML 则属于可复用的测试输入配置，保存到上次自动测试项目的 `.tools/ProjectData`，与手动日志和截图的输出路径分别定位。项目归属来自工具明确记录的上次自动测试上下文，不能仅凭当前工作目录或 `autoTestOutputPath` 猜测。具体见第 17.2 节。

群战的选择规则另行固定：

- 必须显式选择“群战测试”并提供具体测试名称；优先按规则 testDefName 选择，允许唯一显示名或原完整稳定 ID。输出始终包含规范测试定义名。
- 缺少名称、名称匹配不到或匹配多项时，在执行前报错，不推断或随机挑选。即使文件中只有一项群战，也需要明确指名。
- 普通 `auto`、全量回归、目录扫描及普通 `--scenario-only` 不自动调度群战。目录扫描可以发现定义，但不能据此启动数值评测。
- 普通回归入口显式选中群战定义时，应提示使用群战入口，不将其转换成技能测试或其他口袋地图测试。
- 指定一个群战后，只执行该场景及其明确配置的重复实验；输出中同时显示测试名称、稳定 ID、参战方、地图和统计口径。

只跑外部场景时，报告必须明确没有执行全部普通自动测试。合并运行时，外部场景与普通用例的选择、覆盖关系需要在执行前形成明确计划。

单一模组的回归场景可使用 Suite 的 packageId 作为默认目标。群战测试和配装展示可能混合原版与多个模组的内容，允许不指定单一 packageId，改由依赖清单描述所需内容；一旦声明替代覆盖，每个覆盖键仍必须解析出明确的 packageId。

## 4. 推荐的场景结构

| 部分 | 职责 |
| --- | --- |
| `Requirements` | 游戏版本、依赖模组、必需 Def、所需适配能力 |
| `Templates` | 可复用的 Pawn、装备、健康和其他配置 |
| `Coverage` | 回归场景补充或替代哪些普通自动测试目标；群战不使用此映射 |
| `Scene` | 地图、天气、温度、无雾、摆放范围等环境条件 |
| `ScenePresets` | 可复用的地图生成器、环境及布局组合 |
| `Teams` | 阵营、阵营关系及敌友角色 |
| `Actors` | Pawn、建筑、普通 Thing、尸体以及分组 |
| `Steps` | 准备、DebugAction、攻击、施放、等待、截图等步骤 |
| `Success` | 回归场景的成功条件、组合方式、数量和观察范围 |
| `GroupCombat` | 群战数值评测专属的战斗起止规则、AI 策略、伤害口径、各方统计与实时显示 |
| `Presentation` | 整套配装、三视图方向、姿态、图像布局及展示信息 |

`Requirements`、`Templates`、`Scene`、`ScenePresets`、`Teams`、`Actors` 及通用动作、条件由不同测试类型共享。`GroupCombat` 是群战测试的专属配置块；拟议的 Case 类型标识使用 `kind="groupCombat"`，另需可指名的 `name`。群战的 `Scene` 必须解析为普通主地图后端，实时显示使用 `GroupCombat` 内的 `Overlay` 配置。技能测试及其他口袋地图测试继续使用各自的执行逻辑和成功判据，可以直接消费共享场景定义，无需转换为群战测试。

每条可独立运行的 Case 规则必须包含 `<testDefName>`，其值由作者填写，在全部加载文件和 Suite 间唯一，按大小写不敏感检查；缺失、空白和重复均在执行前报错。该定义名属于外部测试系统，不写入模组本体或注册到游戏 Def 数据库。

测试身份分为：

| 字段 | 含义 |
| --- | --- |
| testDefName | 规则自己的唯一稳定定义名，用于选择、结果关联及重跑；移动文件和重复执行不改名 |
| targetDefName / 目标列表 | 被测游戏对象的 DefName，可以一个或多个；同一个目标可以由多条不同测试规则验证 |
| caseId | 规则参数、变体和重复实验展开后的执行实例标识；同一计划唯一，跨运行结合 runId 定位 |
| Suite ID、Case id、步骤/目标 ID | 组织及局部引用身份，不能替代必填 testDefName |
| name | 用户可读显示名，可重复；按显示名选择时需唯一匹配 |

例如 `Axolotl_Move_AppliesHediff` 与 `Axolotl_Move_LandingView` 是两条不同规则，可以共同针对 `Axolotl_SkillMove`。一条规则可关联多个游戏 Def，参数矩阵和重复实验展开为不同 caseId，并保留原 testDefName。testDefName 不使用每次变化的 GUID 或时间戳；输入内容另记哈希。

注册、去重、报告、日志与截图不能继续仅以被测 DefName 作为自定义规则键。目标引用使用 `caster`、`enemies[0]`、`turret`、`corpse` 等逻辑 ID，不依赖小人名字、屏幕坐标或翻译后的菜单文字。

“敌人”“友军”首先是场景角色，实际敌对性仍由游戏阵营关系决定。不能仅分成两个角色组，就假设原生攻击和技能目标判定一定认为它们敌对。复用已有阵营时要校验关系；创建临时阵营或改变关系时，要纳入场景资源管理与清理恢复。

## 5. 可配置的目标

| 目标 | 建议配置 | 关键要求 |
| --- | --- | --- |
| Pawn | PawnKind、生成约束、阵营、位置、装备、服装、特性、工作技能、Hediff、Ability | 正常生成并完成初始化，再做明确覆盖 |
| 建筑 | ThingDef、材料、品质、朝向、生命值、阵营、供电、燃料等 | 供电、燃料等由组件适配，不直接猜测私有字段 |
| 普通 Thing | ThingDef、材料、品质、堆叠、生命值、位置、所属容器 | 不支持的属性明确报错，不静默跳过 |
| 尸体 | 来源 PawnKind、内层 Pawn 配置、死亡方式、腐烂阶段 | 先生成完整 Pawn，再通过正常死亡流程产生尸体 |

其他非 UI 类型还可引用地形区域、RecipeDef 与工作台、HairDef/HeadTypeDef/BodyTypeDef、GeneDef/XenotypeDef 等定义和目标参数；这些不必作为普通 Thing 生成。四类实体表不构成自定义范围上限。

尸体不能只创建一个没有正确内层 Pawn 的空对象。复活、吞噬和尸体技能可能依赖种族、身体部件、健康状态及装备。尸体和内层 Pawn 应分别保留引用，以便验证“尸体被消耗、同一 Pawn 恢复存活”等状态迁移。

分组可规定数量、队形、间距、起点和共同配置。所有对象需要归属到当前场景，清理和矩形选择均以此归属为边界。

## 6. PawnKind 继承与局部覆盖

建议采用“原生生成，再局部覆盖”。PawnKind 本身不是一个完整、固定的角色快照，最终状态还会受到种族、背景、随机生成和模组生成逻辑影响。

用户已明确：角色模板至少能生成 Pawn，未定义属性由基底与原生规则随机补齐，不以数据不完整为由判断暂存角色不可用。显式属性按给定值或范围处理，明确的非法 Def 或无法满足的约束仍报告具体配置错误。

推荐顺序：

1. 确定 PawnKind，以及年龄、性别、阵营等生成约束。
2. 通过正常生成流程建立 Pawn，并完成必要的模组初始化。
3. 按配置的阶段完成生成、出生或地图生成回调。
4. 应用局部覆盖，执行必要的状态刷新。
5. 执行场景准备动作和 DebugAction。
6. 等待准备条件实际满足，检查生成结果是否符合配置。
7. 建立基线，开始真正的行为与效果验证。

装备、服装、特性、技能、健康效果等类别建议统一支持：

| 模式 | 含义 |
| --- | --- |
| `inherit` | 保留原生生成结果 |
| `patch` | 只增加、移除或替换明确指定的部分 |
| `replace` | 清空该类别后使用指定列表 |

例如保留原生服装，只替换帽子；保留背包，只换主武器；保留其他特性，只设置一个特性的等级。

覆盖规则还需明确：

- 缺少配置字段表示继承；清空某类别必须显式使用清空或 `replace` 规则。
- 替换服装时可按明确 Def 等条件匹配，并规定匹配不到时失败还是允许新增。不能无声删除其他装备。
- `Skills` 表示射击、近战、医疗等工作技能等级；`Abilities` 表示特殊技能，两者分开。
- Hediff 需要支持严重度、身体部位等；身体部位使用稳定定义和路径，不按中文显示名称匹配。
- 机械族、动物或特殊种族缺少对应 tracker、不能穿某件衣服、没有指定部位时，应判为准备条件不成立。
- 特殊能量、修炼层级和模组组件状态通过固定适配或 DebugAction 准备，不承诺添加 AbilityDef 后自动补齐全部依赖。
- 覆盖完成后必须验证实际状态。模组可能在后续 tick 中重新应用约束，不能只以 setter 执行成功作为准备成功。

### 6.1 首版采用 PawnKind 风格的数据写法

首版角色模板参照游戏 PawnKind：普通字段用子节点，列表通常用 `<li>`，数值范围沿用 `最小值~最大值`。原生已有的 race、年龄、性别、服装/武器标签和预算、forcedTraits、skills、abilities 尽量保留原名称和语义；明确装备、Hediff 和其他测试专用覆盖作为工具扩展。数据契约和解析器由工具自行实现，游戏侧适配到原生生成和行为 API，不承诺完整原生 Def XML 兼容。

```xml
<PawnTemplate id="temporaryPawn">
  <basePawnKind>Colonist</basePawnKind>
  <race>Human</race>
  <minGenerationAge>20</minGenerationAge>
  <maxGenerationAge>35</maxGenerationAge>
  <apparelTags>
    <li>IndustrialBasic</li>
  </apparelTags>
  <apparelMoney>350~600</apparelMoney>
  <skills>
    <li>
      <skill>Shooting</skill>
      <range>10~15</range>
    </li>
  </skills>
</PawnTemplate>
```

上例没有定义性别、其他技能或具体装备时，按原生规则生成；给出范围的字段在范围内随机。模板仍是工具外部数据，不作为 PawnKindDef 加入模组 Def 数据库，不开放任意原生私有字段。正式字段表和可运行示例在第一批一并交付。

已加载的基底 Def 保持只读；精确换装、更新已有 Hediff 或指定身体部位由专用准备逻辑调用原生 API。正常生成可以继承原生 startingHediffs 和配装行为，局部覆盖不重新执行清空服装的生成流程，也不新增这些原生数据类型的通用导入层。

## 7. 步骤、观察和成功条件

建议第一版提供固定动作集合：生成和摆放、装备及状态准备、原生攻击、原生施放、条件等待、截图，以及受限 DebugAction。

在这个公共内核上，全部非 UI 类型分别提供适用的动作和条件，例如配方实际执行、生长阶段/年龄/外观准备、健康和尸体状态观察。每类允许显式配置目标、适用角色状态、环境、步骤、时间和判据，不能只换目标名而保留不可调整的固定逻辑。各批次按逐类矩阵交付。

主动技能默认走原生可用性和施放流程，不能默认跳过冷却、资源、目标限制或职业要求。若某场景确实需要强制方式，必须显式声明，并记录采用了哪些旁路。

被动技能则可以通过伤害、死亡、环境变化等刺激触发，不应一律套用“下达施放命令”的判断。

| 条件类别 | 示例 |
| --- | --- |
| Pawn 状态 | 存活、倒地、死亡、生命值变化、身体部位状态 |
| Hediff | 存在、不存在、新增、移除、严重度达到范围 |
| Thing | 新创建、出现在地图上、数量增加、被销毁 |
| 技能 | 施放被接受、开始吟唱、完成吟唱、进入冷却、消耗次数 |
| 战斗 | 命中、受到伤害、指定目标死亡、指定建筑受损 |
| 尸体 | 生成尸体、被消耗、内层 Pawn 复活 |
| 截图 | 渲染就绪、目标进入视野、截图生成成功 |

组合逻辑建议限定为 `All`、`Any`、`Not`，并提供 `any`、`all`、至少几个、恰好几个等数量规则。目标数量为零时不能因为“全部满足”就通过。

必须区分以下语义：

- “已经存在某 Hediff”与“本次施放后新增某 Hediff”。基线应在准备动作之后建立。
- “新创建 Thing”与“原有物品从装备、背包或容器中掉到地图上”。旧物身份需要纳入基线；严格创建事件可通过引擎事件适配补充。
- “当前满足”“观察窗口内曾经满足”“整个观察窗口持续满足”。短暂效果不能只在最后一帧检查。
- 多个目标曾分别满足，与同一时刻所有目标共同满足，需要明确表达。

超时使用实际时间；技能持续时间、稳定观察次数等可以使用游戏 tick。时间单位必须写清楚，暂停时的超时仍要生效。

短暂 Hediff 和瞬时生成物应按游戏 tick 观察，必要时接入新增、移除和生成事件。效果观察不能只依赖截图帧率。

截图测试还要区分“取得截图”和“验证技能效果”。截图前建议验证地图、无雾、目标视野、相机稳定和渲染状态。文件存在不能单独证明画面正常；像素或参考图比较可作为额外能力，不默认把所有暗图判为失败。

对回归场景，严重日志、执行异常和清理失败仍应参与最终判定。自定义效果条件满足，不代表可以忽略运行过程中出现的其他真实错误。群战单独记录执行状态和测量质量，按第 14 节输出数值结果，不套用回归场景的通过率和 Bug 判定。

测试执行中的失败要完整记录，完成本次对象清理和环境恢复后继续后续测试项及后续运行批次，不因失败结果弹出人工确认或结束整个测试序列。失败仍保持失败，不由后续成功覆盖；显式取消按取消指令处理。

## 8. 固定格式 DebugAction

游戏原生 DebugAction 有 `Action`、`ToolMap`、`ToolMapForPawns`、`ToolWorld` 等类别。部分动作打开子菜单，部分动作只是设置等待鼠标点击的工具，不能直接调用菜单入口后就认为业务动作已经执行。

建议工具提供稳定动作注册表，XML 仅写 `actionId` 和固定目标选择格式：

```xml
<DebugAction actionId="example.fillEnergy">
  <Select mode="single" actor="caster" />
</DebugAction>

<DebugAction actionId="example.prepareTargets">
  <Select mode="rectangle"
          minX="20" minZ="20"
          maxX="40" maxZ="30"
          filter="enemies" />
</DebugAction>
```

建议限制：

1. 动作必须已登记，具有固定参数、目标类型及无交互执行方式。
2. 选择模式仅为 `single` 和 `rectangle`；矩形按测试地图坐标解析，不模拟鼠标，不使用电脑控制技能。
3. “所有人”使用覆盖场景的矩形和 `allScenePawns` 筛选表达；是否包含死亡或未生成目标需要明确规则。
4. 选择范围限定于当前场景拥有的对象，不遍历或影响主地图上的其他单位。
5. 记录实际目标集合、执行步骤、执行前后状态及异常。
6. 需要子菜单、再次点选或自由文本输入的原生动作，先提供专用适配，不能在场景运行时等待人工操作。
7. XML 不指定任意类名、方法名或私有字段路径，不嵌入代码。

DebugAction 可以插在顺序步骤中，例如“等待生命值低于阈值 → 执行准备动作 → 再施放技能”。不需要首版就引入无限循环或完整脚本事件系统。

准备动作应尽量位于效果观察开始之前。若观察期间的 DebugAction 自己写入了被断言的 Hediff 或生成了期望物品，就不能直接将变化归因于技能。必须记录干预；没有可靠因果追踪时，避免这种会混淆验证的动作组合。

固定格式不能使任意 DebugAction 自动具备场景局部性，注册和适配时仍需确认它的实际行为。

本节的无交互限制针对 XML 场景执行期间调用的准备动作。第 17 节另外新增暂存角色与普通自动测试弹窗，由玩家选择目标和内置类别后开始批次；它们不自动开放为 XML 中可调用的任意动作。

## 10. 补充、替代与一对多覆盖

建议覆盖键至少为：

```text
packageId + defType + defName + caseType
```

有变体的自动用例，还需要能够限定变体范围。仅按 DefName 替代会误覆盖同一个 Def 的信息卡、视图和战斗等不同检查。

这里的 defName 指被承接的游戏目标定义，不是 XML 规则的 testDefName。覆盖映射要同时保存规则身份、实例及对应目标键；不同测试定义名允许针对同一目标，但不解除两个 replace 争用同一覆盖键的冲突规则。

覆盖目标未单独指定 packageId 时，建议沿用所属 Suite 的 packageId；解析后的覆盖键必须包含完整信息。

| 模式 | 行为 |
| --- | --- |
| `supplement` | 普通用例与外部场景都执行，分别保留结果 |
| `replace` | 精确匹配的普通用例由外部场景承接，替代优先于批量上限，其他检查按剩余额度执行 |
| 只跑外部场景 | 调试指定场景，不宣称完成全部常规测试 |

一份配置可以关联多个 DefName，但声明必须对应真实执行与验证：

- 同一套逻辑测试多个技能时，推荐参数矩阵展开，每个技能独立生成环境、施放并验证。
- 联合场景同时验证多个 Def 时，必须有相应动作和期望；不能只测 A 却把 B、C 都计为通过。
- 首版联合场景可以采用保守的整体判定：整个场景失败时，关联目标都不算已验证通过。需要更细粒度时，再绑定每个覆盖目标的具体断言证据。
- 两份 XML 替代同一覆盖键时默认报冲突，不根据文件顺序隐式覆盖。
- 替代场景缺失、未执行、跳过或失败时，对应覆盖不能算成功。
- 区分合法 XML 未命中本次常规范围与引用不存在的 Def/错误覆盖键。前者在有剩余批量额度时仍执行，后者明确报配置错误，不能静默忽略。
- 历史失败报告保持原样，不通过后来编写 XML 将历史结果改成成功。

建议分别维护“实际执行计划”和“目标覆盖映射”。报告应区分执行了几个场景、替代了几个普通用例、验证了几个目标，不能将一次联合执行伪装成多次测试。

用户已明确优先级：先替代，再处理批量上限。先保留本次范围内全部有效替代并移除被承接的普通用例，再从范围内其余候选补足；若仍有额度，执行没有命中常规范围的合法 XML。矩阵展开和去重后的物理 Case 占执行额度，一个联合 Case 不按覆盖目标数重复占用。

替代数量超过上限时仍保留全部替代，不再增加其他候选，并如实报告超限原因。范围外 XML 未选中时记录批量原因，不伪装成通过或已覆盖。具体额度示例和验收见四批实施计划第 2.2 节。

群战测试作为独立数值评测类型，在计划和结果中单独标识，不参与回归的补充或替代映射，不计入 Bug 回归的通过率、失败数和 Def 覆盖率。群战配置中出现 `Coverage` 应报告用途不匹配。它与技能或其他口袋地图测试共用角色、地图等定义，复用关系不构成回归覆盖。

例如：执行一个回归联合场景，承接三个普通用例；场景失败，则三个覆盖目标尚未验证通过。

自定义技能效果测试不自动验证 Gizmo 界面。效果与截图由非 UI 自定义规则处理，Gizmo 可用性和交互仍交给既有 UI 测试，报告分别标识，不新增 XML UI 场景或以功能通过冒充 UI 通过。

配方等 UI/功能混合用例同样按实际行为划分覆盖契约：功能适配拥有独立动作与证据，替代实际生产不等于替代信息卡或账单窗口检查，既有 UI 检查继续保留。

## 11. 失败分类与报告

建议至少区分：

| 分类 | 例子 |
| --- | --- |
| 定义无效 | XML 字段错误、模板循环、Def 不存在、覆盖冲突 |
| 准备失败 | 能量组件未初始化、缺少健康状态、装备不合法、敌对关系不成立 |
| 行为失败 | 施放被拒绝、目标类型不接受、工作任务无法启动 |
| 期望未满足 | 行为已执行，但观察窗口内未出现要求的效果 |
| 取证失败 | 截图、Gizmo 或其他观察探针发生异常 |
| 清理失败 | 地图、单位、窗口、临时状态或阵营关系未恢复 |

这样“60 秒没施放”就不会继续混合代表所有准备和执行问题。

普通回归报告沿用已确定的偏好：Markdown 明细、Results 和 Screenshot Gallery 只展示失败内容；完整执行结果、原始证据及覆盖映射保留在机器可读产物中。日志去重仍保留发生次数和相关场景。

新增群战测试与配装展示具有不同输出目的：群战完整输出胜负、逐单位/逐方统计和测量质量；配装展示保留成功三视图。群战使用该次独立运行的正式产物，不计入 Bug 回归的通过率和失败画廊。普通弹窗发起的内置展示可进入本次启动汇总，外部 XML 场景按其正式运行产物保存；不改变自动回归默认只列失败的规则。详见第 14、16、17 节。

游戏内 DebugAction 发起的全部手动测试按本次游戏启动统一汇总，保留每次执行的结果和图像供玩家查看。不追加到自动测试报告，不改变自动测试的计数、覆盖映射或历史结论；同一物品手动成功也不能覆盖先前自动失败。详见第 17 节。

场景需要追踪 Actor、地图、操作和日志的关联。无法可靠归属的全局异常应明确标记，不应直接当作每个同时运行技能分别造成的错误，也不能无声丢弃。

## 12. 实现分层与四批顺序

推荐分为输入解析、计划编译、场景执行、效果观察和结果汇总五层。输入层接受外部 XML 或游戏内手动请求；结果层分别提供回归覆盖汇总、群战数值结果、配装展示和手动同类汇总。XML 只描述固定的数据、动作和条件，特殊机制通过登记的适配能力扩展。

共享场景定义及其准备、执行能力先供技能测试和其他口袋地图测试使用。群战测试独立增加群体对抗和统计模块；DPS、承伤等模块的完成情况不阻塞其他测试使用共享定义。

| 阶段 | 内容 |
| --- | --- |
| 第一批 | 外部 XML 公共执行闭环、唯一 testDefName、全部非 UI 契约及逐类清单、基础场景与项目上下文 |
| 第二批 | 全部非 UI 战斗/技能/实际功能自定义适配、固定 DebugAction、地图预设、矩阵与补充/替代映射 |
| 第三批 | 全部非 UI 视图自定义适配、角色数据、普通测试专用弹窗、左右 TAB 批量/统一选择及启动汇总 |
| 第四批 | 独立群战数值评测：指名运行、新主地图、群体对抗、伤害统计、实时榜单及重复实验 |

清理和恢复从第一批建立，不留到第三批。特殊资源和能力适配随第二批及后续技能实际场景逐项补充，不依赖第四批的群战统计。每批具体工作、借用模组的验收方式、完成清单和提交要求见四批实施计划。

当前项目以 1.7 为主要交付和实测环境，首版可先固定这一运行后端。结构应记录目标游戏和依赖版本，不将已有类型名称视为跨版本兼容证明。

可以使用目前的技能问题作为设计样例：浮云渡和螈气斩分别准备原生角色及能量上下文，将技能效果验证与 Gizmo 取证拆开；断尾求生按实际设计描述触发条件、代价和效果；对未观测到施放的技能，先验证资源、状态、目标类型及距离等准备条件。

## 13. 实现前需要固定的契约

以下汇总主要约定，具体批次、首版默认值与验收要求见四批实施计划：

- 不传场景路径时不加载外部 XML；单独运行外部场景需要显式选择。
- 全部既有非 UI 类型均须逐类支持自定义，UI/功能混合用例按行为拆分；验收不得只取少量技能、视图或群战代替全部类型。
- 每条 XML Case 必填唯一稳定 testDefName，跨文件和 Suite 检查重复，与被测 DefName、实例 caseId 分开。
- 目录仅加载专用扩展名，默认不递归；运行开始后固定输入计划。
- 默认补充，替代必须精确声明；冲突默认失败。
- 替代优先于批量上限；没有命中常规范围的合法 XML 在仍有额度时继续执行，不能直接丢弃。
- Pawn 默认继承原生生成结果，覆盖必须明确，配置后验证实际状态。
- 首版角色 XML 采用 PawnKind 风格子节点/列表/区间，未定义属性按原生规则随机补齐，暂存角色不要求完整克隆全部状态。
- 行为默认遵守原生限制；强制方式与调试干预显式记录。
- DebugAction 采用稳定注册 ID，仅单体和矩形选择，不等待人工菜单操作。
- 成功判据区分前置状态与动作后的变化，并明确数量和时间语义。
- 场景对象、临时关系及其他运行状态由工具清理，不允许探针异常阻断恢复。
- 不对 XML 开放任意代码或无限制私有字段写入；模组专属机制通过固定适配扩展。
- 所有日志、结果、截图和测试存档遵守仓库 AGENTS.md 的原始产物约定。
- 群战是独立数值评测，必须显式选择群战类型并指名具体测试，不被普通回归或全量选择自动执行，不参与 Bug 回归覆盖和通过率。
- 角色、配装、阵营、地图等定义供技能测试和其他口袋地图测试共用；群战固定新建普通主地图，完成、取消或异常终止后丢弃本轮地图。
- DPS、输出和承伤分布等统计属于群战测试；群战最多三方，默认以整个战斗观察窗口计算 DPS，所有初始参战单位都进入分布统计。
- 群战默认两个临时敌对阵营；一方全部倒下即判负，默认 180 模拟秒，可自定义；超时按场内存活数比较，少者判负，同数平局。召唤物与转换不做专门扩展。
- 群战屏幕左右分别显示双方，每方具有输出 Top10 和承伤 Top10 条形榜；阵容最多显示当前存活数量最多的五种单位，显示名称、图标/人类角色渲染图和 `X存活数量`，下方显示实时平均 DPS 与承伤。
- 地图预设需要区分真实自然日照和仅用于展示的照明调整，不能将截图变亮等同于太阳机制有效。
- 整套配装展示保留同一角色及完整装备，成功展示图与普通回归失败画廊分别输出。
- 新增两个游戏内动作：暂存测试角色、自动测试。第二项打开左右 TAB 普通测试弹窗，批量选目标、统一选三大类及小类；首次类别全选，开始即关窗，重开还原上次测试选择，不读取手写测试规则。自动角色数据仍位于 ProjectData 并跨重启读取。
- 手动测试首次创建工具管理的正式产物路径，本次游戏启动内全部手动执行追加到该会话；重启后另建汇总，角色 XML 仍跨重启保留。每次执行有独立标识，历史不覆盖，不与自动测试合并。

本轮仅记录方案，不修改现有程序、命令、配置、模组 Def 或技能，不启动测试，也不生成额外测试证据。

## 14. 独立数值评测：群战测试（最多三方）

### 14.1 用途与参与方

本节定义新增的“群战测试”，用途是评测战斗数值和群体对抗表现，与此前发现 Bug 的各类测试分开。主要用于一群单位与另一群单位交战，观察角色、武器、技能、配装和队伍协作的表现。例如：20 只狼与 20 只北极熊对抗，记录各方剩余单位、逐单位伤害、DPS 和分布统计。

每场群战规则同样必须有唯一 testDefName，启动时显式选择群战入口及该名，也可用唯一显示名/原完整稳定 ID。矩阵和重复实验具有各自 caseId。队伍落败、DPS 较低或伤害高于对手都是数值结果，不自动转换成 Bug 或回归失败；场景配置无效、执行中断和测量不完整分别记录。

群战测试复用前文的场景、目标、模板、阵营和准备动作定义，独立负责普通主地图生命周期、群体对抗的启动、调度、结束判断、完整统计及屏幕实时显示。技能测试和其他口袋地图测试也可使用这些定义；本节的 DPS 和承伤统计不作为它们的默认要求。群战不使用口袋地图。

群战使用 2 或 3 方，超过 3 方在配置校验时拒绝。每方可使用前文的 Pawn 模板、数量、装备、特性、技能、Hediff 和 Ability 配置，允许按组编排不同单位。群战结果反映组队、AI、走位、目标选择、射程与地形共同作用下的表现，统计至少细分到每个单位与每一方。

每方具有稳定 ID，逐单位使用 `wolves[0]` 等稳定标识。显示名称可重复，统计身份不能依赖名字。

默认由工具建立两个互相敌对的临时阵营，分别承载双方单位，不借用或改变玩家原有阵营关系。三方配置增加第三个临时阵营并两两敌对。首版不增加联盟或专门的阵营转换逻辑。

### 14.2 战斗起止与结果

所有参战对象生成、装备和状态准备完成后，在同一时刻解除准备限制并启动战斗，避免一方先生成就先攻击。准备、地图加载和首次截图不计入战斗计时。

AI 策略需要声明：原生 AI 行为与工具统一下达的“寻找敌人并攻击”是不同实验条件。20 只动物不会仅凭分组名称就自动按统一策略对抗；阵营关系、可达性和攻击调度需要实际设置和验证。

默认规则已由用户确定：

- 战斗默认 3 分钟模拟时间，即 180 秒/10800 ticks，允许 XML 自定义时长。准备与截图不计入。
- 一方全部倒下即判负，不默认增加复活等待窗口。死亡、逃离或移出场景也不算仍站立的参战者；暂时眩晕但尚未倒地不直接算淘汰。
- 达到战斗时限时比较双方当前场内存活数量，少者判负，相等判平局。倒地但活着的单位计入该存活数，与原来的数量口径一致。
- 同 tick 双方全部倒下判平局。三方时全倒的一方判负，其余方继续至剩一方或时限，超时按存活数排序，最高同数并列。
- 默认无伤害或接敌僵持不提前结束，继续至配置时限；另外的实际时间上限仅用于处理卡死和性能异常。

结果分别记录对抗结局、执行状态和测量质量：对抗结局包括各方获胜/落败、平局、僵持和模拟时限结束；执行状态包括完成、中断、准备失败或清理异常；测量质量包括完整、部分可用和不完整。各方输赢及数值高低均作为结果展示，不按回归 `Success` 判定。正常达到模拟时限或僵持结束也可以形成完整测量，程序异常导致提前停止则保留截止数据并标记执行不完整。

截止时刻冻结统计快照。截图和清理期间继续发生的伤害，不再回写该窗口的数据。若要统计战后流血死亡等结果，应显式配置额外观察窗口。

### 14.3 每方和每单位的数据

| 维度 | 建议数据 |
| --- | --- |
| 身份 | 初始队伍、单位 ID、PawnKind、种族、装备及关键初始属性 |
| 数量 | 初始数量、场内站立、场内倒地、死亡、逃离、未知移除 |
| 输出 | 对敌方结算伤害、同组伤害、自伤、直接输出 DPS |
| 承伤 | 来自敌方、同组、自身、确认环境和未知来源的伤害，以及总承伤 |
| 生存 | 死亡/倒地时刻、存活时间、截止状态；需要时增加恢复站立事件 |
| 分布 | 输出、DPS 和承伤分别计算最高、最低、平均值、中位数，并标出对应单位 |
| 质量 | 未归属伤害、未覆盖的伤害来源、事件缺失或其他度量完整性标记 |

“最后剩多少只”默认指仍在场内存活的数量，必须另外列出其中的站立和倒地数量；逃离者单列，不能把倒地或离场直接混成死亡。

死亡单位、零输出单位和未受伤单位仍进入初始参战群体的统计。例如 20 只狼的平均和中位 DPS 按这 20 个成员计算，不能只保留幸存者或有输出者。

首版按场景配置的临时阵营识别双方。召唤物的生成、阵营和行为交给游戏，不新增召唤归属、召唤者贡献或专门的阵营转换账本；通用伤害采集继续记录原生提供的施加者和受击者。

### 14.4 DPS 与分布口径

建议主口径为“整场观察窗口 DPS”：

```text
模拟秒 = 战斗窗口内推进的游戏 ticks / 60
单位 DPS = 该单位在窗口内对敌方造成的引擎结算伤害 / 模拟秒
队伍 DPS = 该方在窗口内对敌方造成的引擎结算伤害 / 模拟秒
```

这里的模拟秒指 60 ticks，不使用游戏历法的小时，也不使用电脑实际耗时。游戏加速、暂停和电脑帧率不应直接改变 DPS 的分母。

所有单位使用同一战斗窗口，包括提前死亡的单位。这样最高/最低与平均值之间可以直接比较。可另外提供存活期间 DPS，但必须单独命名，不能混入上述分布，否则早早死亡的单位可能因分母较短而产生误导。

相同分母和归属完整的条件下，队伍直接 DPS 等于该方全部登记单位直接 DPS 之和。均值以所选群体全部成员计算；偶数个成员的中位数取排序后中间两项的平均。先用未四舍五入数值计算，展示时再取精度。

报告对最高 DPS 单位应同时显示单位 ID、DPS 和累计伤害；承伤也分别列出最高、最低、平均和中位数。

### 14.5 伤害账本与归属

当前战斗探针记录健康比例、命中状态、任务和弹道，新增群战测试必须建立专用伤害事件采集和在线累计，不能只用最终健康比例推算输出。

原生 `Thing.TakeDamage` 返回 `DamageWorker.DamageResult`，其中有 `totalDamageDealt`。建议主指标明确命名为“引擎结算伤害”，避免与武器面板伤害、原始 DamageInfo 数值或绝对生命损失混淆。

建议规则：

1. 记录伤害事件的唯一 ID、时间、直接施加者、受击者、双方编组、伤害类型、武器信息与结算量。
2. 护盾吸收、装甲损耗、Pawn 伤害和建筑伤害分别统计；没有可靠适配时标记不支持或未知，不能重复加到同一个主 DPS 中。
3. 同组伤害、自伤和环境伤害单列，主对敌 DPS 不混入这些数值。
4. 保留原生提供的直接施加者，不为首版额外推导召唤者归属或提供召唤贡献统计，也不反复覆盖游戏自行处理的阵营状态。
5. 无施加者的持续伤害、流血或直接修改 Hediff 的效果不能武断归给最近攻击者。可靠归属不足时保留未知量，并标明 DPS 数据覆盖范围。
6. 同 tick 的多次同额命中是真实独立事件，不能沿用日志的文本去重规则。
7. 对嵌套伤害、反伤和复合伤害建立验证样例，避免同时累计聚合调用与子调用；合法反伤仍需记录。
8. 原生结算量是否包含溢出伤害等，以实际伤害处理器为准。若要另算封顶生命损失，需要单独适配，不能直接把主口径称为已完全剔除过量伤害。

建议输出最多三方的伤害矩阵：每方对其他两方及本组造成多少伤害，确认环境和未知来源作为额外来源类别。总承伤应能与分项及账本核对。

数据质量与战斗胜负分别记录。伤害采集或归属不足时标记度量部分可用/不完整，并写明哪些统计仍可靠；要求精确归属的群战场景可以显式要求完整归属。不满足要求时保留已采集数据并标记未达到测量要求，不将其混入普通 Bug 回归的失败统计。

累计计数器必须持续精确更新。现有操作/日志证据有保留上限，不能在结束时仅对保留下来的事件求和作为整场伤害。详细事件可按工具规范另行记录或采样，但汇总不能因此丢数，并应记录采样与完整性信息。

### 14.6 公平比较与重复实验

通过群战比较武器或配装时，需固定其他角色模板、技能、装备、对手、防护、距离和地图等条件。每场群战需记录站位、AI 策略、地图配置、初始状态及随机种子。

建议支持多个种子重复实验、交换双方出生位置，并输出胜率、剩余数量分布及每场战斗的统计。单场逐单位分布、跨场次队伍分布与合并所有场次的单位分布必须分别标明，不能将“各场中位数的平均”称为“全部单位的中位数”。

固定种子有助于重现，但不保证所有模组随机逻辑都完全可重现，仍需保存实际初始快照与版本信息。

### 14.7 新建普通主地图与丢弃

群战固定创建一张新的普通主地图作为本轮评测场地，使用普通 `MapParent` 及主地图生成流程，不建立 `PocketMapParent`，不挂入口袋地图列表，也不调用口袋地图销毁接口。该地图有真实地图位置和环境，适配所选主地图生成器、自然日照、天气、地形、掩体和布局预设。

建议生命周期为：

1. 解析指名场景并固定输入，记录当前地图/镜头及需要恢复的状态。
2. 在本轮测试环境中新建普通主地图，将其设为当前评测地图，完成地图和单位准备；不复用或清空玩家原有地图。
3. 验证尺寸、站位、敌对关系、可达性和环境，建立基线，同时启动战斗、计时和屏幕显示。
4. 到达结束条件时冻结账本和界面快照，完成结果及需要的图像输出。
5. 先切回原地图或安全入口，再按普通地图的卸载/移除流程丢弃本轮地图、对应世界对象及本轮拥有的单位，释放角色图缓存并恢复临时状态。

完成、取消、准备失败及执行异常均进入同一清理流程。若本轮地图是当前唯一地图，应通过本轮游戏会话的安全退出路径释放，不能调用要求存在其他地图的恢复代码。清理失败要单独记录，不允许接着复用残留场景开展下一轮。

重复实验默认每轮新建并丢弃地图，避免尸体、掉落物、地图破坏及健康残留影响下一次测量。结果、截图及显式要求保留的测试存档继续使用工具管理的原始产物路径；丢弃场景地图不删除已经生成的原始证据。

### 14.8 屏幕实时榜单与阵容显示

两方对战时，屏幕左侧为 A 方、右侧为 B 方，顶部显示具体测试名称、双方名称、战斗模拟时长和当前状态。每方面板显示本方的伤害输出 Top10 与承伤 Top10，两份榜单分别排序、分别以横向条形显示。三方首版采用四批实施计划中的底部居中面板，具体尺寸随屏幕适配。

| 面板区域 | 显示内容 |
| --- | --- |
| 方名与阵容 | 方名；当前场内存活数量最多的前五种单位，每种显示图标/人类角色渲染图、单位类型名称及 `X存活数量` |
| 输出 Top10 | 该方累计对敌输出最高的十个单位，显示名次、单位名称、图标/角色图、伤害条及累计伤害；可同时显示该单位 DPS |
| 承伤 Top10 | 该方累计承伤最高的十个单位，显示名次、单位名称、图标/角色图、承伤条及累计承伤 |
| 下方实时汇总 | 截至当前的人均 DPS、总承伤及人均承伤，另显示当前存活/初始数量；团队总 DPS 可另列并明确标签 |

显示规则：

- 两方各自拥有输出榜和承伤榜，伤害榜与承伤榜的排序互不影响。单位不足十个时显示实际数量，不补虚构单位。
- 两方的同一指标使用相同条形刻度，便于直接比较；伤害输出和承伤各自有独立刻度。
- 排行按累计伤害排列，同值使用稳定单位 ID 确定顺序。死亡或离场单位保留已有成绩，并标注状态，避免将高输出阵亡单位从榜单和统计中抹掉。
- 排行单位显示角色自己的名称和身份；阵容区显示单位类型名称。人类角色图从实际生成并完成配装的 Pawn 渲染，呈现其体型、外观和装备，不以通用人形图标代替。其他单位显示可辨认的单位图标。
- 阵容按明确的显示编组统计：建议以 PawnKind 和指定配装/角色模板区分，同一编组的随机发型等外观差异不拆成不同种类。每种使用代表单位图像，数量严格取该组当前场内存活数。
- 每方从当前场内存活数大于零的编组中按数量降序展示最多五种，数量相同按稳定编组 ID 排序。例如 `森林狼 X17`、`重甲步兵 X8`。没有存活单位时显示零存活状态。种类超过五种时保留前五种并显示其余种类数量摘要，完整阵容仍进入结果。
- “当前场内存活”包含站立和倒地存活单位，排除死亡、逃离及已移出评测地图的单位。倒地数量可另列，不能将其直接计为死亡。
- “实时平均 DPS”建议明确为截至当前的人均 DPS：该方累计对敌伤害 / 已推进模拟秒 / 初始参战单位数。死亡与零输出单位仍在分母中，与最终报告保持一致；若增加近几秒的滚动 DPS，必须另列窗口和名称。
- 承伤下方同时显示总量和人均量，人均承伤使用初始参战单位数作分母。战斗尚未推进时，DPS 显示未开始；暂停时保持上次数据，不能因实际时间经过而下降。
- 精确计数器随伤害事件持续更新，界面建议每 250 毫秒刷新排序和文字。角色图缓存复用，配装或外观变化时再刷新，避免每帧为所有单位重新渲染。
- 原先最多三方的能力保留。第三方需要拥有完整的阵容、两份 Top10 和实时汇总；四批实施计划采用底部居中的独立面板作为首版布局，按屏幕尺寸适配并支持必要的区域滚动，不隐藏第三方的统计。

屏幕显示与最终结果使用同一份伤害账本及口径。结束时冻结显示；地图丢弃时关闭该轮显示并释放引用，不将旧榜单带入下一场。

以下仍是拟议结构。`Wolf_Timber` 和 `Bear_Polar` 是本地 1.7 数据中存在的 PawnKind 名称，普通主地图生成器的 `Example...` 名称是假名。双方临时敌对阵营由工具建立；此例通过群战入口指名 `Example_GroupCombat_WolvesVsBears` 执行，显示名仍为 `20只狼对20只北极熊`。

## 15. 地图预设、自然日照与自定义生成器

本节共享预设与环境描述，地图生命周期由所选测试类型决定：群战固定使用新建普通主地图并在完成后丢弃；技能及其他口袋地图测试可以继续选择口袋地图后端。共享定义不表示共用同一张地图，也不强制各类测试使用同一种地图后端。

### 15.1 预设与环境

场景地图不应只有一种地下平地。建议提供可复用预设：

| 预设用途 | 主要条件 |
| --- | --- |
| 日照开阔场 | 自然天空、起始时刻、晴天、无屋顶、无雾、平坦地面 |
| 室内展示场 | 可控照明、屋顶和背景，用于整套装备截图 |
| 掩体交火场 | 掩体、距离、通道、出生区和障碍分布 |
| 近战对抗场 | 统一地面、明确起始距离和可达区域 |
| 自定义生成器 | 引用已经加载的 MapGeneratorDef，并验证生成后条件 |

预设由生成器、地图尺寸、环境和布局组合而成。Case 可以引用预设并覆盖允许的部分，不必重复整套配置。

自然日照与单纯增加环境亮度需要区分。太阳能、户外需求或依赖日照的技能要验证真实天空与光照状态，不能仅把截图调亮就认定满足机制。

应先核对 1.7 口袋地图对天空和地图层级的实际支持。如果某环境确实不能由口袋地图表达，场景层应明确不支持，或使用单独的隔离测试地图后端，不伪造自然太阳条件。

时刻设置、自然时间推进和固定展示照明也是不同选项。不能为了固定太阳反复重置全局游戏 tick，从而破坏战斗时长、冷却和 DPS 计时。

### 15.2 自定义生成的范围

第一种方式直接引用已经加载的 `MapGeneratorDef`。现有口袋地图服务已接受生成器名称，可复用其解析方式；群战另由普通主地图后端执行生成。两者都需要检查生成器是否适合所选地图后端以及依赖的 DLC、生成步骤是否存在。

首版的另一种方式是由外部配置描述工具登记的固定布局能力，按坐标或矩形调用原生摆放接口，生成简单地形、墙、掩体和出生位置。首版不新增 Prefab 或原生房间布局导入入口，不通过 XML 指定任意 C# GenStep 类。

已加载的地图生成器内部可以正常使用游戏自身的 Prefab 或布局能力。组合任意生成步骤、临时生成器对象及其存档重建不列为首版接入；测试配置和地图初始化结果仍需记录，不能直接承诺测试存档可脱离配置独立复现。

生成后的校验至少包括：

- 尺寸、边界和出生区符合预期，各方位置不重叠。
- 必需通路可达；要求封闭或掩体的场景验证布局。
- 地形、屋顶、天气、温度、光照和无雾状态符合配置。
- 截图目标能进入视野；场景清理时恢复主地图与镜头。
- 保存预设、生成器、种子、布局及最终环境快照，便于解释不同地图下的战斗结果。

## 16. 整套配装三视图与玩家展示

### 16.1 展示目标

新增“配装展示”用途：按 PawnKind 继承和覆盖规则准备角色，保留指定的武器、护甲和服装，展示同一套装备在不同方向的整体外观及部位关系。

这与单件衣服或武器的隔离预览有所区别。展示整套配装时不能为了某件物品自动剥掉其他装备，应在拍摄前核对最终实际穿戴和武器列表。

建议支持：

- 角色的 PawnKind、种族、体型、性别、年龄及外观参数。
- 完整服装、护甲、主武器及相关配件的 Def、材料、品质、颜色等。
- 静立、持武器或瞄准等明确姿态，避免武器在未持用时不可见。
- 正面、侧面、背面三视图；非对称装备可额外增加另一侧。
- 标题、装备清单及可选的部位/服装层覆盖信息，帮助玩家理解整套组合。

### 16.2 一致性与画面

优先对同一个准备完成的 Pawn 依次转向拍摄，确保发型、体型、颜色和装备一致。若使用多个展示对象，也必须来自同一份明确视觉状态，不能将三次随机生成的不同角色当成一个角色的三视图。

固定背景、光照、天气和拍摄尺度，等待方向和渲染稳定后取图。镜头范围需要覆盖头饰、背包、长武器等完整边界，避免裁切。

可以输出一张横排三视图合成图，同时保留三张原图，均由工具生成到本轮原始产物位置。是否隐藏 UI、使用透明背景或添加装备标注需要显式配置，不能默认改变展示目的。

### 16.3 结构示意

以下仅演示展示部分，角色 `presenter` 应在同一个 Case 的 `Actors` 中准备；所属 Case 仍需必填唯一 testDefName，Presentation id 只是局部块标识。Def 和名称仍需按真实配装填写。

```xml
<Presentation id="completeLoadout"
              actor="presenter"
              kind="loadoutThreeView"
              pose="weaponReady"
              preserveFullLoadout="true">
  <Views>
    <View id="front" rotation="South" />
    <View id="side" rotation="East" />
    <View id="back" rotation="North" />
  </Views>
  <Output purpose="presentation"
          layout="horizontal"
          retainIndividualImages="true"
          showEquipmentList="true" />
</Presentation>
```

成功展示图进入配装展示内容区，普通回归的失败画廊继续只列失败内容。展示生成完成不自动代表整套配装具有特定战斗强度；需要时应再引用同一角色配置运行群战测试。

## 17. 游戏内普通自动测试：专用弹窗与本次启动汇总

### 17.1 入口及定位

新增两个由玩家在游戏内主动点击的顶层 DebugAction，名称暂定如下：

| 入口 | 玩家操作 | 执行结果 |
| --- | --- | --- |
| 暂存测试角色 | 选中或点选一个 Pawn，点击录入 | 将当前角色数据写入上次自动测试项目 `.tools/ProjectData` 下的角色 XML，作为后续适用测试的角色来源 |
| 自动测试 | 打开类似刷物品的专用弹窗；左 TAB 多选目标，右 TAB 统一勾选类别，点击开始 | 运行内置普通测试，整个批次共用一套类别，需要角色时优先使用自动暂存数据 |

这是由玩家手动发起的普通自动测试入口，支持反复批量选择和查看结果，不要求手写测试 XML。目标和类别选择后点击“开始测试”，保存选择、提交批次并立即关闭弹窗，无第二次确认；重新打开显示上次实际提交测试的选择。

弹窗参照既有刷物品窗口的视觉、筛选、多选及滚动体验，执行通过内部服务，不模拟电脑鼠标键盘。新增顶层动作只有这两项；目标、类别、参数、角色状态及进度在窗口内处理，不新增规则文件选择器。

### 17.2 暂存角色 XML 与项目归属

暂存的是录入时刻明确写出的角色生成数据，测试时据此准备新的 Pawn，不将玩家原 Pawn 直接送入战场、脱掉装备或修改健康状态。已录入字段固定，未录入或未定义字段沿用基底和原生随机；不要求完整复制原角色全部内部状态。玩家原角色之后的变化不应悄悄改变已经写入的 XML。

建议录入范围：

- PawnKind、种族、性别、年龄、体型和可重建的外观信息。
- 已支持的基因、异种及其依赖信息，缺少对应能力时标明限制。
- 武器、服装、护甲及需要的背包物品，包含 Def、材料、品质、颜色和当前可支持的状态。
- 特性、工作技能等级及热情等可配置数据。
- Hediff、严重度及稳定身体部位路径，必要的身体部件状态。
- 原生 Ability 及已登记适配支持的特殊资源或模组能力。
- 来源角色标识、快照 ID、录入时间、游戏及依赖版本、支持范围和未能录入的字段。

暂存角色明确保存为外部 XML，跨游戏重启保留。默认使用最近录入的角色，建议固定文件名为 `temporary-test-pawn.xml`：

```text
<上次自动测试项目根目录>\.tools\ProjectData\temporary-test-pawn.xml
```

目录沿用现有 `ProjectDataPaths` 的项目路径解析规则，文件名仍属拟议契约。这个 XML 是 PawnKind 风格的共享 `PawnTemplate` 生成输入，允许只描述部分属性，其余随机补齐；不保存完整游戏世界，不作为原生测试存档，也不因存在这个文件就自动执行测试。文件不进入模组 Def 数据库，不部署到游戏 Mods，不随发行包或 Workshop 上传，沿用 `/.tools/ProjectData/` 的 Git 忽略规则。

角色详情可以显示并修改已支持字段，保存时更新快照版本和内容哈希。单个固定文件默认代表当前暂存角色，写入采用原子替换，失败时保留上一个有效文件；是否提供多个命名角色模板另行扩展。

项目定位与读取规则：

1. 工具在正式开始自动测试时，将经过校验的项目根目录绝对路径、项目身份、游戏版本及运行标识传给游戏，并持久化“最近自动测试项目”上下文。记录不以测试通过为条件，也不应随单次测试配置恢复而丢失。
2. “暂存测试角色”动作根据该上下文解析 `.tools/ProjectData`，将角色 XML 直接写到该项目。不能把本模组源码目录、Steam 部署目录、当前游戏存档目录或最近的任意日志目录当成项目根目录。
3. 后续需要暂存角色的手动测试，从该项目载入角色 XML；内存可以缓存，但应按项目身份和内容哈希判断是否仍然有效。角色数据在重启后仍可读取，不再局限于当前游戏会话。
4. 新一次自动测试切换了项目时，角色归属随新的上下文定位，不能将 A 项目的内存角色缓存误当成 B 项目的暂存角色。每次测试记录实际使用的项目和角色快照。
5. 没有有效上下文、原项目不存在或文件不可写时，明确提示缺少的项目条件；可在同一入口显式绑定有效项目。不能静默回退到别的项目或临时目录。角色 XML 缺失或依赖不满足时，遵守对应测试的角色准备规则并明确说明。

现有代码核对结果：项目运行数据目录确为 `<项目根目录>/.tools/ProjectData`，由 `RimDevTools/Infrastructure/ProjectDataPaths.cs` 定位，已经忽略于 Git 并排除部署/发行；当前游戏设置仅记录自动测试输出路径等信息，没有专门的最近自动测试项目根目录字段，因此上述上下文记录属于需要新增的实现。

角色配置使用可重建的数据，不只保留原 Pawn、装备或 Hediff 对象的引用。模组私有状态需要固定适配，未录入部分按原生规则生成，不因此把整个暂存角色标为不可用。每次物品测试从选定配置重新准备 Pawn，避免上一轮受伤、死亡、资源消耗或掉落物影响下一轮，并记录实际生成结果及种子。

每次执行开始时固定本次载入的角色数据、快照 ID 和哈希，将实际输入纳入该次原始结果。后续重新录入并更新当前 XML，不改变已经开始或已经完成的测试输入；不为保存历史额外复制角色 XML 到任务或日期归档目录。

### 17.3 左右 TAB 与统一批量类别

第二项只调度具有内置默认策略的普通测试，不运行需要手写 XML 的测试规则。由两个独立选择区和一个提交区组成：

| 区域 | 交互 |
| --- | --- |
| 左 TAB：物品/目标 | 图标、名称、DefName、模组/来源、多选框；可搜索名称/定义名/模组，按模组、类型/分类、第三方、已选筛选；支持全选当前筛选与清空，筛选/滚动不丢选择 |
| 右 TAB：测试类别 | 战斗、UI、三视图三个大类及小类；首次无记录时全选，重开恢复上次测试类别；大类全选/取消及部分选中，整批只用一套共同类别 |
| 底部 | 已选目标/类别数、预计执行项、适用性及角色状态；开始测试立即提交并关窗，另有关闭或取消 |

左侧覆盖内置测试需要的物品、建筑、Pawn/PawnKind、Ability、Recipe、Hediff、Terrain、Gene、Xenotype、Hair、HeadType、BodyType 等对象/定义，不限定 ThingDef，也不列外部测试规则。

三个大类的显示范围：

- 战斗测试包含炮塔、远程/近战武器、服装/护甲、动物、机械族、异族和技能等内置小类；原 Misc 技能归此。具有内置策略的功能验证放在其子组，不新设第四个大类。
- UI 测试包含全部已有信息卡、窗口/账单等普通 UI 检查。
- 三视图测试包含全部内置角色、装备、年龄/外观/基因/异种三视图，以及植物生长、建筑、地形等其他视图小类。

大类全选作用于该类全部已交付子类，不受折叠影响；左侧全选只作用于当前筛选目标。每个物品不单独指定模式。开始时根据“已选目标 × 统一类别”形成适用任务，不适用组合显示原因，没有可执行项则明确提示。

每次开始保存最近提交的目标身份和类别标识，重新打开还原它们，不按当前列表序号恢复，也不重置为全选。未开始的草稿不覆盖上次测试选择；无历史记录才使用首次全选默认，失效项明确标记。选择记忆与每次游戏启动新建结果会话分别管理。

勾选只修改配置，点击开始保存并冻结批次、分配 InvocationId 后立即关闭弹窗，释放配置暂停。内部任务各有 caseId，串行执行；失败记好结果、清理后继续后续测试项/运行批次，不要求人工确认。运行中重新打开仍显示上次提交的选择，不强制暂停或修改正在执行的计划。

需要角色时可读取“暂存测试角色”自动生成的 PawnTemplate 数据，缺省属性按原生规则生成；该数据不包含测试步骤、判据或覆盖映射，不要求用户手写测试 XML。精确换装保留未修改的装备，显式错误按字段诊断，不暗中使用玩家其他 Pawn。

普通弹窗不读取上次 CLI 的自定义场景路径、规则缓存或替代映射，也不出现规则/文件选择器。所有任务通过内置执行能力发起并明确标记为游戏内手动来源，不开启完整 auto 扫描、不复用自动 RunId 或发出自动完成信号。弹窗验收与外部 XML 自定义验收分别记录。

### 17.4 本次游戏启动内统一汇总

用户已明确，“同类”就是本次游戏启动时全部手动执行的测试，不按物品、检查类型、子项目或不同点击分开。需要区分：

- `GameLaunchId`：本次游戏进程启动的稳定标识，回主菜单、切换存档不重置。
- `ManualSessionId`：本次启动所有手动执行共同使用的唯一汇总会话。
- `InvocationId`：每次点击“开始测试”提交的批次标识，批次内多个目标/类别各有独立 caseId。
- 目标 Def、子项目类型、角色 XML、输入项目及参数：每次执行的分类和输入，不作为拆分会话的依据。
- 来源通道，例如 `manualDebug`：标识由普通自动测试弹窗发起，与 CLI 自动测试等其他入口分别管理。

第一次真正执行手动测试时，由工具分配正式产物路径；本次启动后续全部手动测试复用它。退出游戏后会话结束，下次启动的首次手动测试创建新路径，不续写上次启动的结果；暂存角色 XML 则独立跨重启保留。

该统一汇总保存本次启动内普通测试弹窗提交的全部 UI、战斗/技能、视图及其他内置功能批次，目标与实例分别保留。外部自定义运行的产物按对应入口保存，不追加到这里。

建议流程：

1. 游戏进程启动时建立 GameLaunchId，首次实际执行手动测试时由正式产物管理器分配 ManualSessionId 和路径。
2. 本次启动的后续手动操作直接追加同一路径中的日志、结果及截图。日志和截图由测试服务写入登记的原始位置，不经复制或脚本归档。
3. 每次开始创建新的 InvocationId，批次内各项生成独立操作/案例标识及不冲突的截图名，保留此前记录；汇总按物品和批次查看。
4. 同次启动切换项目上下文时，角色 XML 按实际输入项目读取，手动输出仍使用首次分配的启动会话路径，并记录每次的输入项目，避免拆成多个汇总。
5. 执行结束时更新本次会话的汇总视图，保留每次原始结果。退出游戏时结束该会话，旧记录只读保留；新启动不因找到旧索引而继续追加。
6. 游戏内显示实际状态和路径，内部沿用 `result.artifacts` 的产物描述约定，不由界面猜测目录。

现有测试路径分配主要在 CLI 入口，新增功能需提供游戏侧可调用的正式手动会话分配和续写能力，不能将上次 autoTestOutputPath 当成手动会话。首次手动执行不要求先运行自动测试，缺少项目上下文时按入口的明确绑定规则处理。

手动原始日志应保留跨执行记录，去重仍能追踪每次发生；不能仅用新执行的内存日志重写并抹掉此前内容。本次手动会话的保留与自动测试清理分开。当前路径不存在或不可写时如实提示，交由正式产物管理能力处理，不回退自动测试路径或另拼临时目录。

这里的首次路径属于新增功能自身的正式产物路径，不是执行本策划任务时自建证据目录。本轮不实际创建手动测试目录或迁移既有产物，保留和清理由工具负责。

### 17.5 与自动测试隔离及执行约束

- 手动会话按本次游戏启动统一维护路径、结果、日志关联及汇总，不复用自动测试的 RunId、产物会话指针、自动结果文件或报告。读取最近自动测试项目上下文仅用于定位角色 XML 的项目归属，不代表合并测试结果。
- 不将手动追加写入先前的自动测试目录，不改变自动扫描的发现数、计划数、执行数、通过率或 Def 覆盖关系。手动结果不触发 CLI 自动测试的完成信号。
- 手动汇总保留每次通过、失败、不支持及对应图像，供玩家查看；自动测试报告继续保持失败明细和失败画廊的既定规则。
- 每次执行都记录来源、时间、目标、角色快照、参数和支持范围；本次启动内合并保留全部独立执行，不用最后一次结果覆盖之前的失败。
- 日志去重保留重复次数和对应执行标识，同一条日志出现在哪次执行仍可追踪。测试之外的普通游玩日志不能无依据地归到某次测试。
- 同一时间串行执行手动测试；已有自动测试或场景执行占用资源时显示忙碌状态，避免切换全局日志路径、地图或角色准备状态造成串写。
- 每次执行结束、失败或取消时都清理本次测试对象、恢复镜头和临时状态。共用的是产物会话和角色快照，不共用上一轮已经受损的场景对象。
- 游戏内手动入口的生成与选择流程属于玩家操作，不要求也不使用电脑控制技能。
