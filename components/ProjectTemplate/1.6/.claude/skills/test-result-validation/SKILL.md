# 测试结果校验

对 auto/XML 自动测试结果进行校验，判断失败用例是否构成真实 bug，并产出测试结果校验文档。

## 核心原则：自动测试不是绝对真理

1. 自动测试在人为构造的测试环境中运行：自动生成小人、口袋地图、强制渲染、直接调用游戏内部 API、绕过暂停等。测试方式本身存在局限性，可能误报 bug。
2. **不会被正常游戏流程产生的"bug"不算 bug，只能算作测试方式错误导致的问题，不列入修复。** 只有正常游戏流程中玩家可达的操作才会产生的问题，才可能是真实 bug。
3. 每项测试都有确定的测试流程和核心调用函数（见 [references/test-flows.md](references/test-flows.md)）。校验结果前必须先还原该用例的测试流程，再判定失败原因。

## 结果分类

- **真实 bug**：正常游戏流程可复现，属于当前模组的问题，需要修复。
- **测试误报**：正常游戏流程不会产生该问题，是测试方式、断言或测试框架的局限所致，不修复。
- **环境问题**：模组依赖缺失、版本不匹配、测试基础设施故障等，不列入修复，另行说明。

## 校验步骤

1. 读取测试产物：最终 JSON（`ok`、用例清单、`MissingCaseIds`、`FailedAssertionIds`、`ScreenshotPaths`）、`.tools/log/精选日志.log`、`RimWorldProcess.log` 与截图。不要仅凭进程退出码或缺少可见报错推断成功。
2. 对每个失败用例，在 [references/test-flows.md](references/test-flows.md) 中找到对应测试流程，明确该用例调用的核心函数与断言。
3. 结合日志堆栈、截图与断言信息判断失败原因。
4. 关键判定：该问题是否会在正常游戏流程中出现？
   - 是 → 真实 bug，进入修复流程。
   - 否 → 测试误报，不修复，只在文档中记录。
5. 对疑似真实 bug，用最小化的正常游戏操作路径复现验证，多次测试确认稳定性后再定性。

## 误报常见原因（不列入修复）

- 测试构造了正常游戏不可达的状态（强制生成的 pawn/派系、口袋地图、强制技能可用等）。
- 断言期望值或时机错误（截图早于渲染完成、等待超时过短等）。
- 测试框架自身的局限（渲染抑制、三视图呈现器解析失败、关闭追踪不匹配等）。
- 测试对象缺少依赖、不在目标模组范围或未被正确解析。

## 测试流程文档

[references/test-flows.md](references/test-flows.md) 记录了每项自动测试的流程与核心函数。校验前必须先阅读，禁止凭空猜测测试行为。

## 测试结果校验文档

对确认的 bug 必须撰写测试结果校验文档，保存为项目根目录 `测试结果校验_<yyyyMMdd>.md`（可追加到已有同名文档）。每个 bug 单独一节，必须包含：

1. **Bug 原因**：问题根因分析。
2. **出现的测试流程**：模块名 + 流程名（对应 references/test-flows.md）。
3. **测试对象的名称与 DefName**。
4. **出现的报错**：日志摘录、异常堆栈、断言信息或截图路径。
5. **复现步骤**：如何复现此 bug。
6. **稳定性**：多次测试下能否稳定复现（稳定复现 / 偶发 / 仅首次出现）。
7. **修复优先级**：P0–P3 并给出理由。

优先级标准：

- **P0**：游戏崩溃、存档损坏或阻断主要功能，且处于正常游戏高频路径。
- **P1**：功能错误但可绕过，处于正常游戏常见路径。
- **P2**：次要问题，影响小。
- **P3**：不影响功能的瑕疵。

文档末尾附汇总表：条目、分类（真实 bug / 测试误报 / 环境问题）、DefName、稳定性、优先级、是否修复。

## 交付

- 对每个失败用例给出明确结论：真实 bug（附文档）或测试误报/环境问题（说明原因）。
- 不把误报当作 bug 修复，不为了让测试静默而修改正常行为。
- 交付时说明校验依据：使用了哪些产物、对应哪些测试流程、依据什么判定标准。
