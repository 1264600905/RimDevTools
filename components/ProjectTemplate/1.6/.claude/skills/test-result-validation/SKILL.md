# 测试结果校验

对 auto/XML 自动测试结果进行校验，判断失败用例是否构成真实 bug，默认在聊天中给出结论；仅在用户明确要求时写入校验文档。

## 测试产物与归档

- 日志、结果、截图和测试存档只读取工具生成的原始产物。除用户明确要求导出外，禁止自建 evidence、任务或日期归档目录，包括 `.tools` 和 `.tools/log` 下的额外目录，也不得换到其他目录绕过。
- 禁止通过 `>`、`2>`、`Tee-Object`、`Out-File`、`Set-Content` 或文件复制另存工具 stdout/stderr 和测试产物；禁止为归档编写一次性包装脚本。
- 新版工具以成功 JSON 的 `result.artifacts` 或失败 JSON 的 `error.details.artifacts` 定位本轮产物；字段为 `directoryPath`、`syncLogPath`、`autoTestOutputPath`。旧版没有这些字段时读取已有 LogSync 设置和产物定位，不创建替代路径或补造文件。路径是输出位置，文件是否生成仍需检查。
- 直接在聊天中报告结论并引用原始路径。除用户明确要求外，不另写测试报告或校验文档；保留与清理由工具负责，不修改原始证据。历史测试产物不构成启动新测试的授权。

## 核心原则：自动测试不是绝对真理

1. 自动测试在人为构造的测试环境中运行：自动生成小人、口袋地图、强制渲染、直接调用游戏内部 API、绕过暂停等。测试方式本身存在局限性，可能误报 bug。
2. **不会被正常游戏流程产生的"bug"不算 bug，只能算作测试方式错误导致的问题，不列入修复。** 只有正常游戏流程中玩家可达的操作才会产生的问题，才可能是真实 bug。
3. 每项测试都有确定的测试流程和核心调用函数（见 [references/test-flows.md](references/test-flows.md)）。校验结果前必须先还原该用例的测试流程，再判定失败原因。

## 结果分类

- **真实 bug**：正常游戏流程可复现，属于当前模组的问题，需要修复。
- **测试误报**：正常游戏流程不会产生该问题，是测试方式、断言或测试框架的局限所致，不修复。
- **环境问题**：模组依赖缺失、版本不匹配、测试基础设施故障等，不列入修复，另行说明。

## 校验步骤

1. 读取 stdout 最终 JSON，并按返回的 `artifacts` 读取本轮精选日志、AutoTest 结果和已有截图（包括 `ok`、用例清单、`MissingCaseIds`、`FailedAssertionIds`、`ScreenshotPaths`）。新版不生成 `RimWorldProcess.log`，不要为补齐该文件另存进程输出。不要仅凭进程退出码或缺少可见报错推断成功。
2. 对每个失败用例，在 [references/test-flows.md](references/test-flows.md) 中找到对应测试流程，明确该用例调用的核心函数与断言。
3. 结合日志堆栈、截图与断言信息判断失败原因。
4. 关键判定：该问题是否会在正常游戏流程中出现？
   - 是 → 真实 bug，进入修复流程。
   - 否 → 测试误报，不修复，在聊天中说明判定依据。
5. 对疑似真实 bug，用最小化的正常游戏操作路径复现验证，多次测试确认稳定性后再定性。

## 误报常见原因（不列入修复）

- 测试构造了正常游戏不可达的状态（强制生成的 pawn/派系、口袋地图、强制技能可用等）。
- 断言期望值或时机错误（截图早于渲染完成、等待超时过短等）。
- 测试框架自身的局限（渲染抑制、三视图呈现器解析失败、关闭追踪不匹配等）。
- 测试对象缺少依赖、不在目标模组范围或未被正确解析。

## 测试流程文档

[references/test-flows.md](references/test-flows.md) 记录了每项自动测试的流程与核心函数。校验前必须先阅读，禁止凭空猜测测试行为。

## 测试结果校验文档

仅当用户明确要求保存校验文档时，写入用户指定路径或更新已有文档；未指定保存位置时使用 `mod_config.jsonc` 的 `project_paths.planning_docs` 下固定的 `测试结果校验.md`，复用该文件，不按日期或任务新建目录。默认将以下内容直接报告在聊天中：

1. **Bug 原因**：问题根因分析。
2. **出现的测试流程**：模块名 + 流程名（对应 references/test-flows.md）。
3. **测试对象的名称与 DefName**。
4. **出现的报错**：日志摘录、异常堆栈、断言信息或截图路径。
5. **复现步骤**：如何复现此 bug。
6. **稳定性**：多次测试下能否稳定复现（稳定复现 / 偶发 / 仅首次出现）。
7. **修复优先级**：P0–P3 并给出理由。

优先级标准：

- **P0**：游戏崩溃、存档损坏或阻断主要功能，且处于正常游戏高频路径。
- **P1**：功能错误但可绕过，处于正常游戏常见路径。
- **P2**：次要问题，影响小。
- **P3**：不影响功能的瑕疵。

聊天结论或用户要求保存的文档末尾附汇总表：条目、分类（真实 bug / 测试误报 / 环境问题）、DefName、稳定性、优先级、是否修复。

## 交付

- 对每个失败用例给出明确结论：真实 bug（说明原因并引用原始产物）或测试误报/环境问题（说明原因）。
- 不把误报当作 bug 修复，不为了让测试静默而修改正常行为。
- 交付时说明校验依据：使用了哪些产物、对应哪些测试流程、依据什么判定标准。
